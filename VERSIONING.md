# Contribution protocol SemVer

The new [opensiro/upstream](https://github.com/opensiro/upstream) versions its **operating procedure**, not the target project's release, VSM Profile, Skills Methodology, Index assessment, legal mandate, evidence schema or autonomous permission. The active version is [VERSION](VERSION) with [CHANGELOG.md](CHANGELOG.md) and [changes/](changes/) packages.

**Separate versioned main state from a published Release.** `VERSION` describes the currently integrated protocol snapshot in `main`; it does **not** establish a Git tag, GitHub Release or owner sign-off for publishing one. The authoritative release list is [GitHub Releases](https://github.com/opensiro/upstream/releases). Preserve all historical integration commits and change packages when consolidating releases; never rename or delete intermediate versions as if they had not existed.

**Continuity:** [upstream-old CHANGELOG](https://github.com/opensiro/upstream-old/blob/main/CHANGELOG.md) owns historical **v0.1.0–v0.11.0** packages and their real commits. The new repository **prospectively continued at v0.12.0, published v0.17.0 and v0.18.0, and subsequently integrated advisory v0.18.1 guidance into main without retroactively asserting a separate published tag**, with a fresh Git history (not cloned commits or retroactive tags). [Migration notes](docs/MIGRATION.md).

## Experimental 0.x rules

- **MINOR** (`0.y.0`): an **owner-agreed consolidated release** with independently changed admission, evidence, source/fork preparation, publication, stage or operator workflow. Changes may be accumulated and reviewed first under **Unreleased**, without an automatic bump for each normative PR. Historical merged main revisions v0.12.0–v0.16.0 and their original provenance remain unchanged; a GitHub Release exists only if first-party tag/Release readbacks prove it.
- **PATCH** (`0.y.z`): fix an implementation or documentation mismatch without imposing a newly intended obligation.
- **MAJOR**: reserve `1.0.0` for an expressly stabilized protocol. Once 1.x, incompatible changes require a major bump.
- New issues, PRs, source observations, native tests, sessions, dashboard outputs, forks and editorial corrections **do not themselves require a version bump**.

## Agreement-first version and release workflow

1. **Develop and review.** Put prospective normative changes in a reviewable internal PR with source/evidence and tests; record the intended change in a single **`## Unreleased`** section of `CHANGELOG.md` (or its referenced rolling proposal). **Do not bump `VERSION` or require a fresh `changes/vX.Y.Z.md` for every isolated improvement, batch, research result or PR.** Merge does not by itself publish a Release or grant effectful authority.
2. **Bundle and agree.** Collect compatible, already merged/reviewed changes since the **last verified published tag**, check their source-owned history, compatibility, required actor/permission gates and actual tests; prepare **one consolidated candidate** with a complete changelog and known limitations. Explicitly obtain the owner's agreement on the chosen scope and target version before finalizing the numbered release.
3. **Version the agreed bundle.** In **one final release PR**, update `VERSION`, `CHANGELOG.md`, the consolidated `changes/vX.Y.Z.md`, and any references/tests **together**; run consistency and source-native checks applicable to the actual changes. Use the appropriate SemVer class relative to the last published release and respect pre-existing main version history. Do not rewrite previous packages, merge commits or past evidence.
4. **Publish separately with authorization.** Only after the final release scope, exact reviewed commit SHA and required owner approval are confirmed, create an immutable matching `vX.Y.Z` tag and publish **one GitHub Release** at that commit. Read back the tag, exact commit and Release. A passed CI run, reviewable PR or merge alone is **not** authorization to tag/release.

Link to upstream-old historical packages instead of rewriting old test or batch provenance. A historical issue retains the protocol actually in force when its work was performed; applying new rules to its **future decisions** never asserts old evidence was obtained with a later protocol.

An immutable Git tag `vX.Y.Z` may be created on the validated integration commit when an authorized tagging method is available. Do not claim a tag or release exists without verifying it. A `VERSION` file alone does not prove what a runner read, which external PR was merged or whether a human granted exact publication consent.

**Permissions are independent:** changes to SemVer cannot grant S5 delegation, target-code write rights, CLA/DCO assent, external PR approval or maintainer acceptance.

## GitHub Releases

When an **owner-agreed** release is published, it must refer to a validated integration commit on this repository's default branch. Its immutable `vX.Y.Z` tag must match `VERSION`, `CHANGELOG.md`, and the corresponding `changes/vX.Y.Z.md` package at that commit. Release notes must describe the **protocol change** and explicitly disclose unfinished implementation, migration or outcome verification when applicable.

A GitHub Release is a distribution/navigation point for an already reviewed protocol state, **not** another SemVer increment or an authorization grant. Do not backfill a predecessor tag, release date, test claim, or commit into this repository's fresh history. If tagging or publication is unavailable, report it as pending rather than implying that a GitHub Release exists.
