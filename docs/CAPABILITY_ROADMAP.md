# Capability Roadmap — architecture-first, plan-only

[Protocol](../PROTOCOL.md#architecture-first-upstream-roadmap-ownerrepo-plan-only) · [fork-local roadmap Issue template](../templates/FORK_CAPABILITY_ROADMAP_ISSUE.md) · [external architecture Issue template](../templates/EXTERNAL_ARCHITECTURE_ISSUE.md)

## Purpose

This route tests whether reusable organizational specifications and source-native contributions reduce AI harness engineering effort. **VSM is a working reference hypothesis**, not a required implementation or confirmed cost advantage. The default output is a **decision-ready plan preserved in the matching verified fork plus a fork-local GitHub Issue**, when rights and the separate exact publication approval permit. The process may end with a stored Issue draft and **no public Issue** when publication consent is missing, and with zero product-code changes or original-repository publication.

The normative [Profile](https://github.com/opensiro/vsm-harness-profile/blob/main/PROFILE.md) owns function semantics; [Skills](https://github.com/opensiro/vsm-harness-skills) owns grade/methodology; [Index](https://github.com/opensiro/vsm-harness-index) owns accepted assessments. Upstream does not overwrite their authority.

## Mandatory Index assessment gate for named roadmaps

A named original is **not exempt** from Index-first admission. Before continuing an original-specific `upstream roadmap OWNER/REPO`, read a canonical **accepted included** standalone general assessment in `opensiro/vsm-harness-index` and its matching `data/catalog.psv` repository and `review_ref` at a pinned Index commit. Capture the assessment blob SHA, Profile/Methodology versions and review date, while independently recording the current original HEAD. `status: proposed`, an excluded row, unmerged PR, predecessor assessment or `NOT_ASSESSED` placeholder is insufficient. Missing → **`ASSESSMENT_REQUIRED / BLOCKED`**: complete only lawful preflight and the Index-owned assessment/admission path, **not** another `NEEDS_EVIDENCE` roadmap, speculative `NO_USEFUL_CHANGE` verdict, fork Issue or upgrade. Re-run the roadmap after independent accepted Index `main` readback. This is separate from exact public publication consent.

## Selecting the next original from the accepted Index

Use [the read-only Index-first selector](../scripts/roadmap_select.py) for `upstream roadmap` without a named original, or `upstream roadmap select` when only a shortlist is requested. Only accepted included rows from one pinned Index commit are admitted as candidate inputs. Historical `C/A/P/—/?` signals help identify which *question* to ask, never a presumed missing feature; the cheapest source-native response may be to change nothing. The date-scoped original GitHub metadata, license/formality gate, title-level original issue leads, owner `PAUSE/STOP` and existing case folders are shown separately. A source with no relevant recent issue is `NEEDS_EVIDENCE`, not proven unsuitable. Popularity only diversifies the screening sample; it never proves relevance or merits an S3/S4 function.

The operator/agent must read the full original issues, existing PR diffs/test evidence, original README/code and project contribution policy/CLA before choosing one source for the [named plan-only full cycle](#issue-local-artifact-storage-and-conditional-original-issue). Never automatically emit a public fork Issue, original Issue/PR, a grade change, an autonomous worker or a new contribution record from a shortlist. Dedupe the matching fork's `.opensiro/issues/` with [roadmap view](../scripts/roadmap_view.py); existing Plan/PAUSE cases are not hidden. If no candidate qualifies, return the evidence gap instead of switching to unrelated private/uncurated repositories.

## Original-maintainer-facing Issue — explain the VSM method, don't hide it

The external issue is a **separately approved second public artifact**, not a copy of the internal fork-local Roadmap. Use [`EXTERNAL_ARCHITECTURE_ISSUE.md`](../templates/EXTERNAL_ARCHITECTURE_ISSUE.md) to open with the *specific native proposal* and its current original code/Issues/PRs; then show the **complete accepted historical six-function vector** in an easy-to-scan table explaining **each of S1/S2/S3/S3*/S4/S5** in ordinary language, its accepted state and one source link/limitation. Add the brief Skills-defined `A / C / P / A(P) / C(P) / — / ?` glossary so original maintainers can see that OpenSiro uses an explicit, reviewable methodology without requiring adoption of VSM.

Pin the accepted Index document/commit/blob, its historical source revision, review date and Profile/Skills versions; cite current original HEAD *separately*. Make no quality score, current-grade, safety, shipped-C, maintainer-priority or measured-ROI claim from historical states. Original product design and preferences remain authoritative: source-backed deliberate non-construction, parent S5 and absent stakeholder interest are legitimate. The full internal evidence contract remains linked, not duplicated inline. If no qualified C target or no source-backed original-native proposal exists, no automatic original feature Issue follows. Third-party communication always needs its own exact prior approval and live deduplication.

## Whole-repository six-function census and neutral P0 selection

**Scope:** Read the **whole original repository**, not just the Index cell, one component directory, a surfaced Issue, or a convenient fork patch. Pin source HEAD; map the supported first-party runtime/distribution and system-in-focus; review architecture/docs, source entry points, configuration/policy boundaries, plugins/examples/optional modes, tests and CI, contributor docs and the original's relevant Issues/PRs. Use an explicit inclusion/exclusion map for first-party versus adjacent dogfood/dev/evaluation surfaces; do not credit co-located developer governance to runtime S5.

**First produce all six function dispositions**—S1, S2, S3, S3*, S4, S5—with accepted historical state, actual supported ownership/feedback, candidate C construction, existing and proposed source links, priority reasoning and uncertainty. Missing `—` does not force `C`, and existing `A`/`P` is not a maturity failure. **Deliberate omissions can be valid**: a predictable environment may make S4 adaptation deliberately unnecessary for the selected boundary; ultimate identity/policy may be intentionally parent-governed instead of providing a composable local S5. Require evidence of intent, preserve external/recursion sensitivity and identify the falsifier. Without project evidence, label intention `UNVERIFIED` rather than pretending an absence is intentional. Use these cases to challenge Profile/Skills interpretations **without changing either repository from Upstream**.

**Optional interests:** If maintainers or an OpenSiro contributor have explicitly stated priorities, include the exact attributable source and distinguish the parties. Their interest may affect *feasibility, order or contribution route*, but is **not a condition for architectural evaluation** and not proof of feature demand, rights or a VSM gap. If absent, record `NOT_STATED`, never invent it. Neither VSM nor OpenSiro mandates adding a local S4, S5 or policy subsystem to every harness.

**Selection:** Rank coherent potential target transitions across the **six functions**, with (a) complete function-specific C path and source confidence, (b) minimal additional first-party work and native reuse, (c) lawful authority, reachability and testing, (d) value as a falsifiable methodology experiment, and (e) optional documented contributor/maintainer constraints and expected cost. Choose one P0 transition (`Sx=[accepted historical] → Sx=C`), P1 dependencies and optional P2 **after** ranking; report function-specific exclusions, non-targets and `UNKNOWN` decisions. Operator-specified function constrains target selection but **does not waive whole-repo analysis**. If none qualifies, complete the six-function report and close scoped `NO_GO` or exact external `BLOCKED`, not a fake C.

**Required six-function matrix:**

| Function | Historical Index state | Current source/owner/closure | Candidate `C` or justified no-target | Priority/uncertainty |
| --- | --- | --- | --- | --- |
| S1, S2, S3, S3*, S4, S5 (six separate rows in a real case) | [actual accepted] | [pinned relevant code/doc + boundary] | [C link(s), deliberate exclusion with source, already A/C, parent P, or UNKNOWN] | [P0/DEFER/NO_TARGET/UNKNOWN + reason] |

This is a qualitative prioritization **not an Index reassessment, six-feature quota or guarantee of a contribution**.

The new Human/AI templates must remain source-neutral and function-neutral for S1/S2/S3/S3*/S4/S5.

**One case-local source of truth:** `roadmap.md` (the `proposal-gate` receipt) owns the accepted historical Index vector, six function dispositions, selected transition, P0/P1/P2, proposal-stage verdict, separate research disposition, validation state and publication status. The Human issue.md **renders exactly one six-function historical/current/priority table** and short decision summary **derived from the receipt**; do not add a duplicate historical/current vector table. The AI constructor-sufficiency.md **links** the receipt and Human without copying a second six-row table, and owns pinned source, Track A/B, source-specific C sufficiency and future test criteria. Both Human and AI repeat only the essential `Target transition`, `Proposal-stage decision` and `Research disposition` as derived display fields.

**Acceptance principle, not nine fixed examples:** The agent authors only the original-native tests relevant to the chosen VSM function: lawful positive closure with real feedback, genuinely alternative decisions where applicable, authority/absent-owner negatives and compatibility/feedback failures when supported, and a matched native baseline. Case count, test IDs, and physical port count are **not prescribed**. AI contract lists the **logical organizational requirements** but derives actual interfaces from source, rather than copying Paperclip's port names. Any intentionally inapplicable case receives a source-supported explanation, not a fake test or a guessed native runner.

**Case validation:** For new proposal-gate receipts, run `scripts/validate_capability_roadmap.py <case-dir>` to structurally validate the receipt and check Human↔AI↔receipt links and displayed target/verdict/research status; validate source semantics and GitHub rights separately. The existing single-file invocation and legacy receipts remain supported. **`GO + NEEDS_EVIDENCE` is valid** when a source-grounded complete proposed C construction has not yet been tested or measured; only an essential source/authority blocker merits BLOCKED, and a scoped incoherent/duplicate/no-target design merits NO_GO.

## Default target and work priority

### Proposal-first decision boundary (required)

The purpose of Roadmap is to **propose the minimal complete path from an accepted historical VSM function state to a targeted `C` constructor**, e.g. `S3=— -> S3=C`, not to browse for arbitrary useful capabilities or prove experimental utility in advance.

**Assessment-neutral construction; maintainer-owned product decisions.** Establish whether a source-native first-party construction could satisfy the selected VSM function and `C` classification criteria **after implementation and independent validation**. Do not decide whether the original project needs, wants, should ship or should reject it. Existing code, workarounds, Issues and PRs demonstrate observed behavior and technical constraints; they do **not** establish whether an implementation is temporary or permanent. Cite only explicit maintainer intent, and distinguish it from architectural feasibility. Adoption, replacement and product priorities belong to original maintainers; real authority, contributor and publication restrictions remain binding. Keep three layers independent:

| Layer | Required now | Never claim yet |
| --- | --- | --- |
| **Hypothesis** | Specific original, relevant function, `OBSERVED` or `HYPOTHETICAL` operator scenario, plausible actor/authority/feedback and why it might matter | Incidents, costs or demand not actually observed |
| **Proposal-stage decision** | `GO` for a source-grounded, differentiated and falsifiable design; `NO_GO` for established equivalent function-specific C ownership/closure, incoherent construction or no intelligible new VSM decision/feedback path; `BLOCKED` only for a missing mandatory source/identity/rights fact | Product implementation permission, maintainer endorsement or accepted Index `C` |
| **Validation / Upgrade** | *Future* measured native tests, real task comparison, total cost/benefit, maintainer review, and Index assessment only through Index owner | Treat a plan or proposal GO as successful implementation |

**Proposal GO sufficiency:** a fixed historical state → proposed `C` target; a complete source-mapped function-specific C chain (disturbance/state, eligible options, developer-composed autonomous decision actor, lawful enforcement, actual later operation and returned feedback); the **minimum missing first-party changes** relative to shipped code/Issues/PRs; and falsifiable positive/negative acceptance. A generic useful contribution cannot substitute for a missing C link. The scenario may be deliberately **hypothetical**, and the experiment may be **NOT_RUN**. Missing measurement does not itself imply `NO_GO` or `BLOCKED`. Distinguish confidence in the design from measured benefit. Do not confuse a deterministic S2 task board with an autonomous S3 whole-organization choice, and do not assert S3=C just because the design would allow a future controller.

### Parallel VSM gap → existing work + own on-top proposal

After Index-first admission, complete the **whole-repository six-function census and neutral P0 ranking first**, then declare the selected exact historical function → proposed C target and research Track A and Track B in parallel. Track A maps the actual shipped baseline, relevant Issues (including maintainer decisions), open/closed/merged PR heads and tests, native recipes/plugins/composition and rights. Track B independently develops useful original-native contributions that **reuse, integrate, extend, or complement** A. Both tracks use the **same user task and source revision** for a fair counterfactual; a low historical Index grade or an existing Issue alone is insufficient; **a reasoned proposal does not require prior measured benefit**.

| C-sufficiency link | Existing first-party source/Issue/PR coverage (shipped vs proposed) | Our missing on-top C constructor link, or native reuse | Proposed C witness and falsifier |
| --- | --- | --- | --- |
| [Sx-specific state/options/decision/action/feedback] | [Pinned implementation/Issue/PR, owner, action and return] | [Minimum first-party C port and legal integration, or already supported] | [What makes a developer-composed C actor actually decide and close the function; counterexample] |

Check at least the simplest native alternative and all materially plausible on-top variants within the locked original/function **to identify reusable links, actual C equivalence and integration constraints—not to choose the maintainer's product design**. Explicitly distinguish **reuse unchanged**, **integrate/extend**, and a separately justified **adjacent capability**; if a variant is unsupported, give `HYPOTHETICAL / NOT_TESTED` for a plausible falsifiable design, or source-justified `NOT_APPLICABLE` for an inapplicable variant, instead of fabricating evidence. A maintainer Issue may already solve one narrow task while a distinct developer-composability task remains open. A matching Issue/PR, simpler native bug fix or unmeasured benefit is **not** automatic NO_GO: functional equivalence must be shown at the VSM decision-owner/closure boundary, not just the task level. Neither does a generic guessed adjacent task earn GO without a source-grounded distinct function-specific scenario and falsifier. NO_GO applies to the **declared evaluation object**, never the whole harness.


**Target-first roadmap:** for relevant VSM functions without a confirmed `C`/`C(P)` or `A`/`A(P)` first-party path, investigate the **minimum source-native set of existing and proposed changes sufficient for a meaningful `C` constructor**. Use accepted Index grades only as dated evidence; inspect current source and resolve `?` before concluding a function is missing. Already-`A`/`A(P)` functions **do not need C engineering work** for this roadmap, even though `A` does not logically imply a reusable `C` interface. Already-`C`/`C(P)` functions also do not need another constructor. Parent-governed `P` is legitimate, and may be retained as the final mode when an autonomous constructor adds no user value or violates reserved authority.

**P0** is the highest-priority qualified source-backed function-specific *C sufficiency construction*, chosen after the six-function census, selected **after parallel existing-work and on-top candidate comparison**, backed by the combination of actual first-party primitives, original Issues/PRs and necessary missing changes. **P1** covers **prerequisites** for that target, including integration, authorization and tests; these dependencies may have to execute before P0 can be delivered. **P2** is independently valuable but optional: a separately evidenced `C(P)`/`A(P)` mode, refinements or optimizations. Priority is based on C-construction sufficiency, source confidence, supported authority/reachability, reusable first-party links and technical dependencies. Plausible user benefit and cost remain **separately labeled hypotheses for maintainers**, not proposal GO requirements; historical grades are not an `A > C > P` maturity ladder.

A plan **MUST show the accepted historical state → observed source-native current state → C construction target or justified exclusion → minimum necessary integration set → sufficiency evidence/acceptance** for each relevant function. It is not sufficient to list P0/P1 ideas without specifying why the complete set could later support `C`. For any qualified C target, link a function-specific first-party constructor and positive/negative acceptance contract. A plan does not assert a shipped C; if there is no defensible useful target, `NEEDS_EVIDENCE` or `NO_USEFUL_CHANGE` is a successful **explicit** plan-only outcome. There is no compulsory implementation, new grade or maintainer adoption.

## Issue-local artifact storage and conditional original Issue

`upstream roadmap` remains `PLAN_ONLY`, but a named invocation now aims for the **complete fork-local Issue cycle by default**: resolve the verified matching fork, preserve a case under `opensiro/meta:.opensiro/issues/<case-id>/`, then obtain **separate exact current-conversation approval** before creating the public fork GitHub Issue. An explicitly requested persisted case remains mandatory even if later public consent is not granted. Check fork parent, meta HEAD, owner control, issue duplicates and write authority before effects. Store case-level `roadmap.md`, `constructor-acceptance.md`, external Issue drafts and technical receipts there, **not** in central Upstream. For Opensiro discussion, use the [generic fork roadmap Issue template](../templates/FORK_CAPABILITY_ROADMAP_ISSUE.md), populated with current source-native evidence. A public fork GitHub Issue for discussing/reviewing that case requires a separate exact approval of its full title/body; a case folder alone is not a GitHub Issue. The [external architecture template](../templates/EXTERNAL_ARCHITECTURE_ISSUE.md) is a distinct maintainer-facing artifact and does not become public automatically.

**Persistence completion gate:** for each named `upstream roadmap` full-cycle invocation, and especially when the operator says `зафиксируй`, `оформи в .opensiro` or `до local issue`, record **one verified** case on the actual matching fork's independent `opensiro/meta` branch when effective rights allow. Check fork identity/parent, license, explicit owner control and write authority; dedupe case ID, use `README.md`, a Human decision document, a separately cross-linked AI contract, `roadmap.md` receipt and relevant unpublished draft, with any meaningful attributed event. If the matching fork or metadata branch does not exist, **perform the required creation/bootstrap route below** under the standing roadmap instruction, subject to verified legal and actual provider/org rights; if those checks fail or PAUSE/STOP applies, fail closed with the exact gate. Read back the exact commit and run `scripts/validate_capability_roadmap.py` against `roadmap.md` before saying **PERSISTED**. A chat archive alone is **NOT_PERSISTED**. Metadata storage is distinct from a public fork GitHub Issue, `.opensiro/contributions/`, native implementation or an original Issue/PR publication.

Follow the [fork Issue → case evidence → original Issue route](../PROTOCOL.md#fork-github-issue--local-case--external-issue-separate-publication). Before any original Issue, dedupe the live original issue/PR set; link an existing original issue if it covers the outcome. For a new maintainer issue, request a **separate exact publication approval**, create a standalone original-native issue and read back its actual URL; store/cross-link it in the fork case. This is not GitHub native transfer across separate owners, nor automatic closure of the fork Issue. No grade change, product code implementation or public PR is implied by case publication.

## Missing matching fork — create it during the roadmap

**Required by the owner instruction of 2026-11-18; see [the normative Upstream route](../PROTOCOL.md#architecture-first-upstream-roadmap-ownerrepo-plan-only).** A selected, assessment-qualified `upstream roadmap` must not finish `NOT_PERSISTED` solely because its `opensiro-contributions` fork has not yet been created. This is an execution obligation for a **selected named case**, not for the read-only `roadmap select` shortlist.

1. Verify the accepted Index assessment, pinned original HEAD, root license and contributor restrictions, available authenticated organization fork rights, and absence of a correctly parented existing fork (search alternate names, not only the anticipated slug). Unknown/denied API reads are not proof of absence.
2. When no matching fork exists, **create the public fork in `opensiro-contributions` without another routine user approval**, using the owner's standing roadmap fork-creation instruction. Independently read back GitHub's `fork=true`, exact original parent, default branch and current HEAD. Do not use an unrelated repository with a matching name.
3. Reuse `opensiro/meta` if it exists and is writable under existing owner control. If the ref is confirmed absent, create it from the pinned fork default HEAD and write the initial `.opensiro/state.json` plus the full Human/AI/receipt case in one authorized bootstrap, keeping `.opensiro/` off all product/default branches. For an admitted, owner-directed Upstream roadmap issue-queue case, the 2026-11-19 owner activation supplies an attributable `ACTIVE/ALLOW` mandate: initialize both fields accordingly with a new decision event, **not** automatic `PAUSE/DORMANT`. An explicit later PAUSE/STOP, uncertain/invalid existing metadata, unavailable provider rights or failed legal/admission preflight still blocks effects. This is not public publication consent. Validate and read back the new exact case commit.
4. Block only for an actual original-rights/formalities gate, unavailable fork-creation or metadata-write capability/permission, namespace/parent collision, provider failure, or effective prior owner PAUSE/STOP. Record the exact attempted call and evidence, not a generic "fork missing". Complete all remaining lawful source research and the **GO / NO_GO / BLOCKED** decision without claiming GitHub persistence. Public fork Issues, fork PRs and original-repository communication still require separate exact publication consent.

## One-pass completion and user attention

A named roadmap and a follow-up to "continue to the end" require a **single completed research handoff**, not repeated intermediate waiting states. Intermediate findings, `NEEDS_EVIDENCE` during investigation, the >30-day reassessment advisory and draft artifacts are internal checkpoints, **not user review gates**. Carry through all source-native overlap, legal, functional-sufficiency, alternatives, acceptance and cost checks that remain permitted. If the matching fork is absent, **create it as the mandatory selected-roadmap step under the standing owner instruction and verified provider/legal rights**; if that concrete provisioning fails, complete Human and AI research and the Capability Roadmap Receipt without claiming fork-local files or public Issues, explicitly report `PERSISTENCE_BLOCKED / NOT_PERSISTED`, and name the missing right. If fork metadata exists and public fork Issue approval is absent, finish at `READY_FOR_FORK_ISSUE_APPROVAL — NOT PUBLISHED` with the exact destination, public title/body and verified case commit, not an intermediate waiting checkpoint. Only finish with source-linked `DECISION_READY`, genuinely exhausted `NEEDS_EVIDENCE`, or `NO_USEFUL_CHANGE`; identify any real blocker and its exact next decision. No background execution, inferred implementation mandate, external publication, owner-control override or bypass of exact current-conversation consent follows from this no-intermediate-wait rule.

### Mandatory proposal-stage GO / NO_GO / BLOCKED decision

A complete roadmap reaches one **bounded proposal decision** without demanding experimental results before experimentation:

| Narrative verdict | Proposal-stage gate | Next permissible handoff |
| --- | --- | --- |
| **GO — propose/validate** | A fixed historical function → proposed C target, complete minimum first-party function-specific C constructor design, source-mapped reused/missing links, real actor/choice/authority/effect/feedback and falsifiable native tests; `HYPOTHETICAL`, `NOT_RUN` and `NOT_MEASURED` are allowed | Recommend bounded validation/design next; separate Upgrade authority required for any implementation |
| **NO_GO — decline this proposal** | Both tracks checked; no coherent lawful complete C constructor can be proposed for the named function, or current first-party source already supplies equivalent C ownership/closure | Reject only this specific candidate, preserve other original Issues/opportunities |
| **BLOCKED — necessary fact inaccessible** | Exact mandatory source/assessment/identity or owner-right unavailable after bounded attempts, with evidence owner and conditional unlock | Stop the prohibited action; continue lawful read-only analysis |

A future test proving or disproving the proposed result is part of **Validation**, not evidence required for **Proposal GO**. GO/NO_GO assess architectural C constructibility, **not** product desirability: a simpler bug fix, unknown maintainer preference or unmeasured cost does not independently reject a complete distinct C path. Equivalent current first-party C decision ownership and closure still justify NO_GO. Maintainers alone decide adoption; neither verdict authorizes implementation. Do not use `NO_GO` as a substitute for missing measurements, or `BLOCKED` for weak commercial proof. The research disposition (`DECISION_READY`, `NEEDS_EVIDENCE`, `NO_USEFUL_CHANGE`) is a separate axis: `GO + NEEDS_EVIDENCE` is valid for an untested but qualified proposal. Never relabel the historical Index vector, claim already-shipped `C`, invent passing tests or convert `PLAN_ONLY` to implementation permission.

Repeat the same scoped proposal decision and hypothesis/validation state in Human `issue.md`, AI `constructor-sufficiency.md` and receipt `roadmap.md` **only if fork-local writes are authorized**. On `PAUSE/STOP`, finish the read-only decision and report `PERSISTENCE_BLOCKED / NOT_PERSISTED`. Keep all separate public fork Issue and original maintainer consent gates. This is an actual final research decision, not a request for routine `continue`.

## Procedure

1. **Source and authority pins + whole repo:** Named original repository; exact current default HEAD; observation time; legal license/contributor/AI policy and autonomy preflight; accepted Index assessment URL *and file blob SHA*, historical review date/ref; explicitly label pending reassessments as unaccepted. Declare system-in-focus and excluded recursion. Audit the full repository's current supported modes and all six VSM functions before selecting the priority target; separate product runtime from adjacent docs, examples, dogfood and CI governance. If a verified fork is relevant read original parent and `opensiro/meta` owner controls before writes.
   - **Assessment freshness advisory:** Compute age in calendar days at the observation date from the latest accepted successful Index semantic review (`reviewed_at`, or a later successfully supported `last_checked_at`; do not credit informal source inspection). If older than **30 days**, **recommend an Index-owned, source-pinned re-assessment before relying on the historical vector for architectural conclusions**. Materially changed current behavior can justify the recommendation sooner. Cite the exact canonical assessment, date, current source HEAD and any live reassessment issue/PR. This recommendation is **not** a periodic reassessment mandate, universal Index policy, automated queue write, grade change or roadmap block. If re-assessment is pending or not feasible, continue **plan-only with provisional claims**, old assessment explicitly historical, and source-native evidence controlling current functionality. An open or unmerged proposal is not accepted freshness.
2. **Six-function native work census:** For **each** S1/S2/S3/S3*/S4/S5, inspect shipped native code and architecture; source-backed intentional exclusions; exact relevant original Issue and PR state/head/diff and maintainer decision; existing fork work; alternative native/parent arrangements; whether a C constructor would be justified; explicit no-target and unknowns. Document the whole-function priority ranking before P0. Distinguish `SHIPPED`, `OPEN_PR`, `ISSUE_ONLY`, `EXPERIMENT`, `EXTERNAL_GOVERNANCE` and `UNVERIFIED` as *report labels only*, not stored metadata enums.
3. **Function-specific residual gap:** Name real actor → trigger → decision/action → observable result; actual disturbance; decisive right and owner; enforcement/transport; feedback into subsequent operation. Write `current main → competing proposal → remaining task`, overlap/alternative, uncertainty. No conclusion from a low Index grade or an issue title alone.
4. **Choose P0 after the census; justify C completeness:** Apply the [six-function priority route](#whole-repository-six-function-census-and-neutral-p0-selection) and [default target and P0/P1/P2 order](#default-target-and-work-priority) to *eligible, source-grounded* function candidates, not all historical empty slots. A qualified C implementation target **requires** source-native evidence of the exact user counterfactual, environmental/operational stimulus, first-party function-specific decision/feedback port, independently developer-composable autonomous decision actor and authority boundary, options/state lifecycle, enforcement, return-to-operation receipt, distribution reachability, and positive/negative/compatibility acceptance tests. Identify existing PR/Issue coverage vs remaining edits **and why their combined behavior would be sufficient**. Without those, call it `NEEDS_EVIDENCE`, never implementation-ready `C`. `C(P)`/`A(P)` are optional independent modes only for S3/S4/S5, not mandatory stages; a legitimate `P` can remain final. No shipped or grade assertions from plans. Present simpler native mechanisms as alternatives and reusable links; solving the same task is not by itself a veto on distinct C constructibility.
5. **Independent maintainer choices:** (a) original-native code/PR work, with existing Upgrade gates and separate independent contribution record per real improvement; (b) normative semantic feedback to Profile or separate Skills method/assessment improvement; (c) permitted experimental domain fork with declared boundary. Neither a spec issue nor a fork creates original maintainer obligations.
6. **Matched cost experiment:** Predeclare equivalent native vs VSM-informed user tasks and measure total implementation, integration, review/test, maintenance/regression effort and output quality. Report `NOT_MEASURED` until data exist. Never claim proven cheaper or performance superiority from a diagram.
7. **Handoff:** Save the Human/AI [Capability Roadmap Receipt](#capability-roadmap-receipt) case where authorized, then show the complete public fork Issue title/body and target. Publish/read back the fork-local Issue only after separate current-conversation consent; if consent is absent, report `READY_FOR_FORK_ISSUE_APPROVAL — NOT PUBLISHED`. Keep any independent [external original architecture issue](../templates/EXTERNAL_ARCHITECTURE_ISSUE.md) `DRAFT — NOT PUBLISHED` until its own separate approval. Plan-only requires no product code or PR, and may honestly end at `NO_USEFUL_CHANGE` after exhausted research.

## Explicit implementation follow-up (not part of PLAN_ONLY)

A bare `upstream roadmap OWNER/REPO` request targets the source-linked **fork-local Issue full cycle** (or an exact owner-publication gate with verified case), **without product edits**. When the owner **separately requests implementation of this roadmap/constructor contract, including a fork-local review PR**, it activates the already-defined [full-cycle Upgrade handoff](../PROTOCOL.md#roadmap--implementation-handoff-explicit-execution-intent) for that **same original**. The previous roadmap's `PLAN_ONLY` label describes the *past stage*, not a veto on new implementation intent.

A qualified `C` constructor is **not delivered** by the contract, code sample, fake completion tests or a generic plugin extension. Carry the smallest first-party path from disturbance and proposed options through real developer-composed decision owner, enforced authority, next-operation application and observation. Test the original-native capability delta and contract acceptance cases. Stage implementation/test code on the verified `opensiro-contributions` fork's product branch; keep schema-v2 evidence on `opensiro/meta` only. Prepare original-template PR diff and five-link handoff. If that gate remains unapproved, report the tested branch plus `READY_FOR_FORK_LOCAL_PR_APPROVAL — NOT PUBLISHED` rather than falsely marking a PR complete. ## Capability Roadmap Receipt

A compact **plan-only Markdown report** accompanies a dated **case record in the verified fork's `.opensiro/issues/<case-id>/`** when full-cycle persistence is effectively authorized. The intended final artifact is a public fork-local Issue opened **only after its own exact current-conversation owner approval**; otherwise report `READY_FOR_FORK_ISSUE_APPROVAL — NOT PUBLISHED` with the exact stored case. A chat-only report caused by missing rights is a blocked fallback, not successful full-cycle publication. Do not create an Upstream queue or an implementation contribution ID merely for the proposal. Required evidence sections:

| Section | Required contents |

| Identity | Original and HEAD SHA/date; boundary/recursion; pinned accepted Index assessment SHA, review date/ref and Profile/Skills refs; last successful review/check date, age in days and any proposed re-assessment link (provisional when pending) |
| Human-first presentation | Why Opensiro → complete central accepted six-system VSM baseline (historical grades/meaning/provenance) → prioritized human decision and explicit link to separate AI/developer construction contract; no bulky technical appendix embedded in the Issue |

**Fail closed:** unknown source/ref/owner/diff or assessment freshness stays unverified. A >30-day historical assessment prompts a recommended re-review, not a hard stop, automatic Index write, or silent promotion of a pending reassessment. An Issue or open PR does not certify shipped capability, a planned `C` is not an Index `C`, and a maintained project policy is not automatic runtime S5.
**Receipt shape (C-transition proposal-stage opt-in):** New cases use `- Receipt contract: proposal-gate`; the canonical receipt owns `- Accepted VSM vector: S1=A · S2=A · S3=A(P) · S3*=A · S4=— · S5=P` (illustrative only), six per-function dispositions, `- P1 dependencies:`, `- P2 optional:`, `- Research disposition: NEEDS_EVIDENCE` / `DECISION_READY` / `NO_USEFUL_CHANGE` independently of proposal GO/NO_GO/BLOCKED. This structurally separates qualified plans from measured results. Existing `contribution-on-top` and unmarked historical receipts remain valid without retroactive edits; the validator does not certify semantics, actual source validity or execution. Never invent `VALIDATED` from a proposal GO.

For an implementation-oriented `C` target, see the [Paperclip S4=C proposed construction and acceptance contract](https://github.com/opensiro-contributions/paperclip/blob/opensiro/meta/.opensiro/issues/model-release-adaptation-20261117/constructor-acceptance.md) for a concrete (still plan-only) first-party interface/ownership/feedback design and falsifiable test matrix. ## Optional structural receipt check

The source-native receipt remains **PLAN_ONLY evidence in the fork metadata worktree**, not an implementation contribution, a public Issue, a fork-local review PR or Index assessment. For a dated Markdown case note, run:

~~~sh
python3 scripts/validate_capability_roadmap.py /path/to/fork-meta/.opensiro/issues/<case-id>/roadmap.md
~~~

The validator checks presence of pinned SHA/date fields, required receipt sections, an evidence link and explicit non-publication/cost status. In `<case-dir>` mode for new `proposal-gate` cases, it also compares target, verdict, research disposition, and displayed historical states across Human/AI and canonical receipt. It cannot detect semantic source-mapping mistakes. **It does not read live GitHub, verify legal permissions, prove VSM function closure or certify lower cost.** Exact current GitHub readback and semantic review remain mandatory before any subsequent action.

## Ownership and stages

- The roadmap is **not** an Index reassessment, normative Profile patch or second canonical ledger.
- Existing single-harness `upstream upgrade` remains the implementation route, with material capability-delta, native tests, v2 provenance, verified matching fork and separate exact public approvals.
- Fork-local `.opensiro/contributions/<id>.json` remains **one independently implemented improvement**, on the separate `opensiro/meta` branch; a roadmap may link existing records without manufacturing a new case.
- A public original issue, comment or PR is a separate external interaction and needs a complete exact approval in the current conversation. A plan-only route has **no automatic publication**.
