# Capability Roadmap — architecture-first, plan-only

[Protocol](../PROTOCOL.md#architecture-first-upstream-roadmap-ownerrepo-plan-only) · [fork-local roadmap Issue template](../templates/FORK_CAPABILITY_ROADMAP_ISSUE.md) · [external architecture Issue template](../templates/EXTERNAL_ARCHITECTURE_ISSUE.md)

## Purpose

This route tests whether reusable organizational specifications and source-native contributions reduce AI harness engineering effort. **VSM is a working reference hypothesis**, not a required implementation or confirmed cost advantage. The default output is a **decision-ready plan preserved in the matching verified fork plus a fork-local GitHub Issue**, when rights and the separate exact publication approval permit. The process may end with a stored Issue draft and **no public Issue** when publication consent is missing, and with zero product-code changes or original-repository publication.

The normative [Profile](https://github.com/opensiro/vsm-harness-profile/blob/main/PROFILE.md) owns function semantics; [Skills](https://github.com/opensiro/vsm-harness-skills) owns grade/methodology; [Index](https://github.com/opensiro/vsm-harness-index) owns accepted assessments. Upstream does not overwrite their authority.

## Mandatory Index assessment gate for named roadmaps

A named original is **not exempt** from Index-first admission. Before continuing an original-specific `upstream roadmap OWNER/REPO`, read a canonical **accepted included** standalone general assessment in `opensiro/vsm-harness-index` and its matching `data/catalog.psv` repository and `review_ref` at a pinned Index commit. Capture the assessment blob SHA, Profile/Methodology versions and review date, while independently recording the current original HEAD. `status: proposed`, an excluded row, unmerged PR, predecessor assessment or `NOT_ASSESSED` placeholder is insufficient. Missing → **`ASSESSMENT_REQUIRED / BLOCKED`**: complete only lawful preflight and the Index-owned assessment/admission path, **not** another `NEEDS_EVIDENCE` roadmap, speculative `NO_USEFUL_CHANGE` verdict, fork Issue or upgrade. Re-run the roadmap after independent accepted Index `main` readback. This is separate from exact public publication consent.

## Selecting the next original from the accepted Index

Use [the read-only Index-first selector](../scripts/roadmap_select.py) for `upstream roadmap` without a named original, or `upstream roadmap select` when only a shortlist is requested. Only accepted included rows from one pinned Index commit are admitted as candidate inputs. Historical `C/A/P/—/?` signals help identify which *question* to ask, never a presumed missing feature; the cheapest source-native response may be to change nothing. The date-scoped original GitHub metadata, license/formality gate, title-level original issue leads, owner `PAUSE/STOP` and existing case folders are shown separately. A source with no relevant recent issue is `NEEDS_EVIDENCE`, not proven unsuitable. Popularity only diversifies the screening sample; it never proves relevance or merits an S3/S4 function.

The operator/agent must read the full original issues, existing PR diffs/test evidence, original README/code and project contribution policy/CLA before choosing one source for the [named plan-only full cycle](#issue-local-artifact-storage-and-conditional-original-issue). Never automatically emit a public fork Issue, original Issue/PR, a grade change, an autonomous worker or a new contribution record from a shortlist. Dedupe the matching fork's `.opensiro/issues/` with [roadmap view](../scripts/roadmap_view.py); existing Plan/PAUSE cases are not hidden. If no candidate qualifies, return the evidence gap instead of switching to unrelated private/uncurated repositories.

## Two-level case presentation: Human first, AI second

**Reusable artifacts:** [Human Issue template](../templates/FORK_CAPABILITY_ROADMAP_ISSUE.md) and [AI/developer technical contract template](../templates/ROADMAP_AI_CONSTRUCTOR_CONTRACT.md). Fill these with source-native evidence in the same fork-local case folder.

**Template lineage — Paperclip historical pilot.** The current **Human** template follows [the fork-local Paperclip human pilot](https://github.com/opensiro-contributions/paperclip/blob/opensiro/meta/.opensiro/issues/capability-roadmap-issue-pilots-20261118/issue-v2.md): (1) Why Opensiro and central accepted vector, (2) proposed user capabilities and decision, (3) existing native work vs missing capability, (4) P0/P1/P2 and minimum sufficient result, (5) acceptance/stop, (6) independent paths, (7) cost, (8) handoff. The **AI** template follows the [Paperclip technical contract](https://github.com/opensiro-contributions/paperclip/blob/opensiro/meta/.opensiro/issues/capability-roadmap-issue-pilots-20261118/constructor-sufficiency-v2.md): functional scope (S2/S3/S4/S5) first, then historical boundary/counterfactual, verified shipped-vs-proposed evidence, primary construction ports, dependency order, optional independently justified secondary constructor (or `P2: NONE`), native acceptance, falsification/evidence ownership. **Only structure is generalized**: Paperclip's `S3=A(P)`, `S4=—`, specific feature and tests are not universal facts. A real instance must cite its own accepted Index and current original source, and maintain the same vector, P0/P1/P2, rights and stop verdict across both levels.

**The human-facing Issue is the entry point**, not the condensed tail of the technical design. Its first substantive content MUST follow this order:

1. **Why Opensiro:** Opensiro tests whether VSM-informed reusable specifications and source-native integrations can **standardize and lower the engineering cost of AI-agent harnesses**. Cost reduction is an unmeasured hypothesis; maintainers are not obliged to adopt VSM.
2. **Central accepted Index assessment:** a prominent complete **`S1/S2/S3/S3*/S4/S5`** vector and compact **six-function table** showing ownership state, meaning and assessment consequence, linked to the accepted assessment, `review_ref`, date, Profile/Skills versions. This is the **historical starting point** of reasoning, not proposed after-state. Never invent missing states; use explicit `?`/`UNVERIFIED` when absent.
3. **Human decision:** operator outcome and counterfactual, original-native alternatives/Issues/PRs, prioritized target vs dependencies vs optional work (`P0/P1/P2`), materiality, stop and no-publication gates, direct link to the AI companion.

**Acceptance example rule:** The AI template's `AC-01…` and optional `AC-OPTIONAL-..` rows are **illustrative placeholders, not mandatory tests**. For every new harness, replace or omit them based on actual pinned source, supported modes, function-specific decision owner, rights and verifiable first-party feedback; add new native cases where necessary. Only **coverage principles** (positive closure, lawful alternative when applicable, negative authority and compatibility/failure cases when applicable, observable feedback, native-baseline comparison) are obligatory. A scenario that does not apply must be omitted with a source-based explanation; neither test names nor test count are normative. Do not mark examples as executed.

Keep this a **short human decision surface**. Do not put the full constructor API specification, source map, multi-step implementation recipe or extended test matrix inline. Put these in **one case-local linked AI/developer contract**, preserving the exact same starting assessment/priority claims. That companion MUST own first-party code/pinned refs, current shipped-vs-proposed gap map, five-link function-specific sufficiency as appropriate, authority and ownership, `S3↔S4` interface when relevant, verifiable native tests including negatives, evidence gaps and implementation stop rules. **Two files are two audiences, not two public Issues**. Cross-link both; use the current approved fork issue template as Human reference.

An optional one-sentence status header is metadata, not the beginning of the substantive presentation. Do not lead with a proposed feature, technology name, a raw vector **without first explaining Opensiro**, or a wall of API details before the central assessment.

## Default target and work priority

### Parallel VSM gap → existing work + own on-top proposal

After Index-first source admission and a plausible VSM function-specific gap, **research two tracks in parallel before selecting P0**. Track A maps the actual shipped baseline, relevant Issues (including maintainer decisions), open/closed/merged PR heads and tests, native recipes/plugins/composition and rights. Track B independently develops useful original-native contributions that **reuse, integrate, extend, or complement** A. Both tracks use the **same user task and source revision** for a fair counterfactual; a low historical Index grade or an existing Issue alone is insufficient.

| Existing native path / source | What it already covers (shipped vs proposed) | Our on-top contribution, or source-backed NONE | Incremental user result and native falsifier |
| --- | --- | --- | --- |
| [Pinned implementation / Issue / PR and state] | [Decision owner, action, feedback already available] | [Reusable primitive + minimum extra integration/constructor/alternative] | [What the developer can now do that was impossible or materially inferior; when no delta → reject candidate] |

Check at least the simplest native alternative and all materially plausible on-top variants within the locked original/function. Explicitly distinguish **reuse unchanged**, **integrate/extend**, and a separately justified **adjacent capability**; if a variant is unsupported, give `NOT_EVIDENCED` or source-justified `NOT_APPLICABLE` instead of fabricating a feature. A maintainer Issue may already solve one narrow task while a distinct developer-composability task remains open. A matching Issue/PR is **not** automatic NO_GO; neither does a guessed adjacent task earn GO without material evidence. NO_GO applies to the **declared evaluation object**, never the whole harness.


**Target-first roadmap:** for relevant VSM functions without a confirmed `C`/`C(P)` or `A`/`A(P)` first-party path, investigate the **minimum source-native set of existing and proposed changes sufficient for a meaningful `C` constructor**. Use accepted Index grades only as dated evidence; inspect current source and resolve `?` before concluding a function is missing. Already-`A`/`A(P)` functions **do not need C engineering work** for this roadmap, even though `A` does not logically imply a reusable `C` interface. Already-`C`/`C(P)` functions also do not need another constructor. Parent-governed `P` is legitimate, and may be retained as the final mode when an autonomous constructor adds no user value or violates reserved authority.

**P0** is the best evidence-backed, incrementally useful function-specific *C sufficiency target*, selected **after parallel existing-work and on-top candidate comparison**, backed by the combination of actual first-party primitives, original Issues/PRs and necessary missing changes. **P1** covers **prerequisites** for that target, including integration, authorization and tests; these dependencies may have to execute before P0 can be delivered. **P2** is independently valuable but optional: a separately evidenced `C(P)`/`A(P)` mode, refinements or optimizations. Priority is based on material user benefit, composability feasibility, reuse of existing work, dependencies and measured-or-hypothesized effort—not the lowest historical grade or a supposed `A > C > P` maturity scale.

A plan **MUST show the accepted historical state → observed source-native current state → C construction target or justified exclusion → minimum necessary integration set → sufficiency evidence/acceptance** for each relevant function. It is not sufficient to list P0/P1 ideas without specifying why the complete set could later support `C`. For any qualified C target, link a function-specific first-party constructor and positive/negative acceptance contract. A plan does not assert a shipped C; if there is no defensible useful target, `NEEDS_EVIDENCE` or `NO_USEFUL_CHANGE` is a successful **explicit** plan-only outcome. There is no compulsory implementation, new grade or maintainer adoption.

## Issue-local artifact storage and conditional original Issue

`upstream roadmap` remains `PLAN_ONLY`, but a named invocation now aims for the **complete fork-local Issue cycle by default**: resolve the verified matching fork, preserve a case under `opensiro/meta:.opensiro/issues/<case-id>/`, then obtain **separate exact current-conversation approval** before creating the public fork GitHub Issue. An explicitly requested persisted case remains mandatory even if later public consent is not granted. Check fork parent, meta HEAD, owner control, issue duplicates and write authority before effects. Store case-level `roadmap.md`, `constructor-acceptance.md`, external Issue drafts and technical receipts there, **not** in central Upstream. For Opensiro discussion, use the [generic fork roadmap Issue template](../templates/FORK_CAPABILITY_ROADMAP_ISSUE.md), populated with current source-native evidence. A public fork GitHub Issue for discussing/reviewing that case requires a separate exact approval of its full title/body; a case folder alone is not a GitHub Issue. The [external architecture template](../templates/EXTERNAL_ARCHITECTURE_ISSUE.md) is a distinct maintainer-facing artifact and does not become public automatically.

**Persistence completion gate:** for each named `upstream roadmap` full-cycle invocation, and especially when the operator says `зафиксируй`, `оформи в .opensiro` or `до local issue`, record **one verified** case on the actual matching fork's independent `opensiro/meta` branch when effective rights allow. Check fork identity/parent, license, explicit owner control and write authority; dedupe case ID, use `README.md`, a Human decision document, a separately cross-linked AI contract, `roadmap.md` receipt and relevant unpublished draft, with any meaningful attributed event. If the matching fork or metadata branch does not exist, **perform the required creation/bootstrap route below** under the standing roadmap instruction, subject to verified legal and actual provider/org rights; if those checks fail or PAUSE/STOP applies, fail closed with the exact gate. Read back the exact commit and run `scripts/validate_capability_roadmap.py` against `roadmap.md` before saying **PERSISTED**. A chat archive alone is **NOT_PERSISTED**. Metadata storage is distinct from a public fork GitHub Issue, `.opensiro/contributions/`, native implementation or an original Issue/PR publication.

Follow the [fork Issue → case evidence → original Issue route](../PROTOCOL.md#fork-github-issue--local-case--external-issue-separate-publication). Before any original Issue, dedupe the live original issue/PR set; link an existing original issue if it covers the outcome. For a new maintainer issue, request a **separate exact publication approval**, create a standalone original-native issue and read back its actual URL; store/cross-link it in the fork case. This is not GitHub native transfer across separate owners, nor automatic closure of the fork Issue. No grade change, product code implementation or public PR is implied by case publication.

These are plan-only fork files, not published GitHub Issues or a current-revision grade.

## Missing matching fork — create it during the roadmap

**Required by the owner instruction of 2026-11-18; see [the normative Upstream route](../PROTOCOL.md#architecture-first-upstream-roadmap-ownerrepo-plan-only).** A selected, assessment-qualified `upstream roadmap` must not finish `NOT_PERSISTED` solely because its `opensiro-contributions` fork has not yet been created. This is an execution obligation for a **selected named case**, not for the read-only `roadmap select` shortlist.

1. Verify the accepted Index assessment, pinned original HEAD, root license and contributor restrictions, available authenticated organization fork rights, and absence of a correctly parented existing fork (search alternate names, not only the anticipated slug). Unknown/denied API reads are not proof of absence.
2. When no matching fork exists, **create the public fork in `opensiro-contributions` without another routine user approval**, using the owner's standing roadmap fork-creation instruction. Independently read back GitHub's `fork=true`, exact original parent, default branch and current HEAD. Do not use an unrelated repository with a matching name.
3. Reuse `opensiro/meta` if it exists and is writable under existing owner control. If the ref is confirmed absent, create it from the pinned fork default HEAD and write the initial `.opensiro/state.json` plus the full Human/AI/receipt case in one authorized bootstrap, keeping `.opensiro/` off all product/default branches. In the absence of an attributable active-owner grant, initialize `PAUSE/DORMANT`; the initial transaction does not waive later PAUSE/STOP. Validate and read back the new exact case commit.
4. Block only for an actual original-rights/formalities gate, unavailable fork-creation or metadata-write capability/permission, namespace/parent collision, provider failure, or effective prior owner PAUSE/STOP. Record the exact attempted call and evidence, not a generic "fork missing". Complete all remaining lawful source research and the **GO / NO_GO / BLOCKED** decision without claiming GitHub persistence. Public fork Issues, fork PRs and original-repository communication still require separate exact publication consent.

## Canonical case filenames

The current canonical case filenames are `README.md`, `issue.md` (Human), `constructor-sufficiency.md` (AI/developer) and `roadmap.md` (receipt), with descriptive draft filenames such as `maintainer-comment-draft.md`. Never propagate a historical pilot's `-v2` / `-vN` filename suffix to a new case. Keep Human-to-AI backlinks in sync and store revisions in Git; preserve historical comparison links and actual contribution `schema_version: 2` semantics.

## One-pass completion and user attention

A named roadmap and a follow-up to "continue to the end" require a **single completed research handoff**, not repeated intermediate waiting states. Intermediate findings, `NEEDS_EVIDENCE` during investigation, the >30-day reassessment advisory and draft artifacts are internal checkpoints, **not user review gates**. Carry through all source-native overlap, legal, functional-sufficiency, alternatives, acceptance and cost checks that remain permitted. If the matching fork is absent, **create it as the mandatory selected-roadmap step under the standing owner instruction and verified provider/legal rights**; if that concrete provisioning fails, complete Human and AI research and the Capability Roadmap Receipt without claiming fork-local files or public Issues, explicitly report `PERSISTENCE_BLOCKED / NOT_PERSISTED`, and name the missing right. If fork metadata exists and public fork Issue approval is absent, finish at `READY_FOR_FORK_ISSUE_APPROVAL — NOT PUBLISHED` with the exact destination, public title/body and verified case commit, not an intermediate waiting checkpoint. Only finish with source-linked `DECISION_READY`, genuinely exhausted `NEEDS_EVIDENCE`, or `NO_USEFUL_CHANGE`; identify any real blocker and its exact next decision. No background execution, inferred implementation mandate, external publication, owner-control override or bypass of exact current-conversation consent follows from this no-intermediate-wait rule.

### Mandatory terminal GO / NO_GO / BLOCKED decision

A **complete** named `upstream roadmap` has one concrete operator decision, not merely a speculative feature draft or another "continue" checkpoint. After exhausting permitted read-only current-source, original issue/PR, existing native workaround, decision-owner/feedback and native acceptance/cost analysis **within the chosen harness and function**, repeat the **same** final decision in the Human `issue.md`, AI `constructor-sufficiency.md` and `roadmap.md` receipt:

| Decision (narrative only) | Evidence required | Immediate action |
| --- | --- | --- |
| **GO** | Source-linked materially new user outcome; simplest native alternative shown insufficient; complete minimum function-specific construction/authority/feedback and falsifiable native acceptance; current competing PR coverage checked | Handoff one narrow source-native implementation proposal; **do not implement** without separate Upgrade intent/rights |
| **NO_GO** | Current source/workarounds or absence of a demonstrated *additional* operator benefit does not justify constructing the proposed capability now | **Do not implement the speculative constructor**. Reuse native solution, link existing original issues, or end research with no change |
| **BLOCKED** | Exact missing **external or owner-owned** evidence after attempted bounded first-party verification, with evidence owner, source attempts and the smallest conditional next action | Do not implement/publish; close all remaining permitted research rather than ask for another routine continuation |

These **are not new JSON status enums**. Retain the existing `Result: DECISION_READY`, `NEEDS_EVIDENCE`, `NO_USEFUL_CHANGE` or `PLAN_ONLY` notation where applicable; a `NEEDS_EVIDENCE` research label is terminal only with **NO_GO or BLOCKED for the present decision**, evidence of exhausted attempts, and a named external unlock. **Missing evidence does not prove `NO_USEFUL_CHANGE`; a new feature is not qualified merely because an accepted Index S-function is `—`**. Prioritization must reflect this verdict: a rejected P0 is a **candidate not authorized work**, and P1/P2 are not automatically a backlog. The report must state what will *not* be done and the reason, source pins, unmatched native option, exact remaining test/owner when truly unavailable, current fork PAUSE/STOP and public publication statuses.

For a paused or dormant verified fork, complete all lawful **read-only research** and the definite decision in chat; do not update `opensiro/meta` or imply a new fork GitHub Issue or authority grant. State `PERSISTENCE_BLOCKED` for the new decision until an explicit effective owner `RESUME`/ALLOW; do not overwrite a previously persisted case with a fictional updated verdict. A fork Issue publication remains a distinct exact current-conversation consent decision.

## Procedure

1. **Source and authority pins:** Named original repository; exact current default HEAD; observation time; legal license/contributor/AI policy and autonomy preflight; accepted Index assessment URL *and file blob SHA*, historical review date/ref; explicitly label pending reassessments as unaccepted. Declare system-in-focus and excluded recursion. If a verified fork is relevant read original parent and `opensiro/meta` owner controls before writes.
   - **Assessment freshness advisory:** Compute age in calendar days at the observation date from the latest accepted successful Index semantic review (`reviewed_at`, or a later successfully supported `last_checked_at`; do not credit informal source inspection). If older than **30 days**, **recommend an Index-owned, source-pinned re-assessment before relying on the historical vector for architectural conclusions**. Materially changed current behavior can justify the recommendation sooner. Cite the exact canonical assessment, date, current source HEAD and any live reassessment issue/PR. This recommendation is **not** a periodic reassessment mandate, universal Index policy, automated queue write, grade change or roadmap block. If re-assessment is pending or not feasible, continue **plan-only with provisional claims**, old assessment explicitly historical, and source-native evidence controlling current functionality. An open or unmerged proposal is not accepted freshness.
2. **Native work census:** For relevant S1/S2/S3/S3*/S4/S5, inspect current shipped code; exact original issue and PR state/head/diff and maintainer decision; existing OpenSiro fork work; competing original alternatives. Distinguish `SHIPPED`, `OPEN_PR`, `ISSUE_ONLY`, `EXPERIMENT`, `EXTERNAL_GOVERNANCE` and `UNVERIFIED` as *report labels only*, not stored metadata enums.
3. **Function-specific residual gap:** Name real actor → trigger → decision/action → observable result; actual disturbance; decisive right and owner; enforcement/transport; feedback into subsequent operation. Write `current main → competing proposal → remaining task`, overlap/alternative, uncertainty. No conclusion from a low Index grade or an issue title alone.
4. **C-construction target, completeness and priority:** Apply the [default target and P0/P1/P2 order](#default-target-and-work-priority) to functions lacking confirmed `C` or `A`. A qualified C implementation target **requires** source-native evidence of the exact user counterfactual, environmental/operational stimulus, first-party function-specific decision/feedback port, independently developer-composable autonomous decision actor and authority boundary, options/state lifecycle, enforcement, return-to-operation receipt, distribution reachability, and positive/negative/compatibility acceptance tests. Identify existing PR/Issue coverage vs remaining edits **and why their combined behavior would be sufficient**. Without those, call it `NEEDS_EVIDENCE`, never implementation-ready `C`. `C(P)`/`A(P)` are optional independent modes only for S3/S4/S5, not mandatory stages; a legitimate `P` can remain final. No shipped or grade assertions from plans. Prefer simpler native mechanisms whenever they meet the operator need.
5. **Independent maintainer choices:** (a) original-native code/PR work, with existing Upgrade gates and separate independent contribution record per real improvement; (b) normative semantic feedback to Profile or separate Skills method/assessment improvement; (c) permitted experimental domain fork with declared boundary. Neither a spec issue nor a fork creates original maintainer obligations.
6. **Matched cost experiment:** Predeclare equivalent native vs VSM-informed user tasks and measure total implementation, integration, review/test, maintenance/regression effort and output quality. Report `NOT_MEASURED` until data exist. Never claim proven cheaper or performance superiority from a diagram.
7. **Handoff:** Save the Human/AI [Capability Roadmap Receipt](#capability-roadmap-receipt) case where authorized, then show the complete public fork Issue title/body and target. Publish/read back the fork-local Issue only after separate current-conversation consent; if consent is absent, report `READY_FOR_FORK_ISSUE_APPROVAL — NOT PUBLISHED`. Keep any independent [external original architecture issue](../templates/EXTERNAL_ARCHITECTURE_ISSUE.md) `DRAFT — NOT PUBLISHED` until its own separate approval. Plan-only requires no product code or PR, and may honestly end at `NO_USEFUL_CHANGE` after exhausted research.

## Explicit implementation follow-up (not part of PLAN_ONLY)

A bare `upstream roadmap OWNER/REPO` request targets the source-linked **fork-local Issue full cycle** (or an exact owner-publication gate with verified case), **without product edits**. When the owner **separately requests implementation of this roadmap/constructor contract, including a fork-local review PR**, it activates the already-defined [full-cycle Upgrade handoff](../PROTOCOL.md#roadmap--implementation-handoff-explicit-execution-intent) for that **same original**. The previous roadmap's `PLAN_ONLY` label describes the *past stage*, not a veto on new implementation intent.

A qualified `C` constructor is **not delivered** by the contract, code sample, fake completion tests or a generic plugin extension. Carry the smallest first-party path from disturbance and proposed options through real developer-composed decision owner, enforced authority, next-operation application and observation. Test the original-native capability delta and contract acceptance cases. Stage implementation/test code on the verified `opensiro-contributions` fork's product branch; keep schema-v2 evidence on `opensiro/meta` only. Prepare original-template PR diff and five-link handoff. A public fork-local PR itself still needs **separate exact current-conversation approval of its destination, action, full title/body and diff**; no blanket authorization is inferred from "implement". If that gate remains unapproved, report the tested branch plus `READY_FOR_FORK_LOCAL_PR_APPROVAL — NOT PUBLISHED` rather than falsely marking a PR complete. No external original publication or grade upgrade follows automatically.

If the native delta or a true S4/S3/etc decision/closure witness is not established, say `NO_MATERIAL_DELTA` or `IMPLEMENTATION_BLOCKED` with source-backed reasons, and do not add a fake first-party controller to fill a grade.

## Capability Roadmap Receipt

A compact **plan-only Markdown report** accompanies a dated **case record in the verified fork's `.opensiro/issues/<case-id>/`** when full-cycle persistence is effectively authorized. The intended final artifact is a public fork-local Issue opened **only after its own exact current-conversation owner approval**; otherwise report `READY_FOR_FORK_ISSUE_APPROVAL — NOT PUBLISHED` with the exact stored case. A chat-only report caused by missing rights is a blocked fallback, not successful full-cycle publication. Do not create an Upstream queue or an implementation contribution ID merely for the proposal. Required evidence sections:

| Section | Required contents |
| --- | --- |
| Identity | Original and HEAD SHA/date; boundary/recursion; pinned accepted Index assessment SHA, review date/ref and Profile/Skills refs; last successful review/check date, age in days and any proposed re-assessment link (provisional when pending) |
| Human-first presentation | Why Opensiro → complete central accepted six-system VSM baseline (historical grades/meaning/provenance) → prioritized human decision and explicit link to separate AI/developer construction contract; no bulky technical appendix embedded in the Issue |
| AI companion | Linked case-local source-to-constructor evidence, current shipped/proposed gaps, owner and authority/feedback chain, native acceptance/negative tests; mirrors the human baseline and priorities |
| Permission | License/contributor/CLA/AI policy, allowed paths and any actual fork owner state; no inferred write |
| Existing work | Original and fork issue/PR URLs, true open/merged status and head/diff evidence, shipped/proposed distinction |
| Parallel on-top review | Declared evaluation object; track A first-party coverage and live Issue/PR decisions; track B independently considered integration/extension/adjacent candidates; native baseline; incremental user benefit/falsifier; reasons for reject/not applicable; exact decision scope (never the whole harness by default) |
| VSM witness | Function, disturbance, real decision/feedback owner/right, enabling first-party primitives and return-to-operation |
| Proposed capability | Actor/output and native alternative, meaningful constructor path, dependencies and small acceptance cases |
| Target matrix and work priority | Relevant functions: accepted historical state, current source witness, `C` target or justified exclusion (already `A`/`A(P)` or `C`/`C(P)`), P0 capability, P1 necessary dependencies, P2 optional modes, and why the proposed *full change set* is sufficient for the C target or explicitly blocked |
| Constructor sufficiency (for each qualified `C` target) | Function-specific first-party ports and distribution reachability; what a developer must compose (real autonomous decision actor/authority), option/state lifecycle, controlled return into future operation, negative cases and reproducible end-to-end acceptance. Explicitly distinguish proposed from shipped `C`. |
| Optional paths | Product-native code, Profile or Skills feedback, permitted domain-specific fork |
| Cost check | Paired native/VSM-informed task, all-in measures and observed values, else `NOT_MEASURED` |
| Delivery | `PLAN_ONLY`, `NEEDS_EVIDENCE` or `NO_USEFUL_CHANGE` as narrative outcomes only; external issue marked `DRAFT — NOT PUBLISHED` |

**Fail closed:** unknown source/ref/owner/diff or assessment freshness stays unverified. A >30-day historical assessment prompts a recommended re-review, not a hard stop, automatic Index write, or silent promotion of a pending reassessment. An Issue or open PR does not certify shipped capability, a planned `C` is not an Index `C`, and a maintained project policy is not automatic runtime S5.
**New receipt shape:** For new cases, put `- Receipt contract: contribution-on-top` in Identity, add `## Parallel contribution-on-top review` and lines for `- Evaluation object:`, `- Existing-work overlap:`, `- Our on-top contribution:`, `- Incremental benefit:`, `- Decision scope:`. The structural validator requires those only when this opt-in marker is present; historical immutable receipts without it remain structurally valid, without claiming they passed the new semantic gate. Source-review accuracy, meaningful alternatives and incremental value still require human/agent semantic review.

For an implementation-oriented `C` target, see the [Paperclip S4=C proposed construction and acceptance contract](https://github.com/opensiro-contributions/paperclip/blob/opensiro/meta/.opensiro/issues/model-release-adaptation-20261117/constructor-acceptance.md) for a concrete (still plan-only) first-party interface/ownership/feedback design and falsifiable test matrix. The example demonstrates required specificity, not a changed Index grade or a mandatory VSM architecture.

## Optional structural receipt check

The source-native receipt remains **PLAN_ONLY evidence in the fork metadata worktree**, not an implementation contribution, a public Issue, a fork-local review PR or Index assessment. For a dated Markdown case note, run:

~~~sh
python3 scripts/validate_capability_roadmap.py /path/to/fork-meta/.opensiro/issues/<case-id>/roadmap.md
~~~

The validator checks presence of pinned SHA/date fields, required receipt sections, an evidence link and explicit non-publication/cost status. **It does not read live GitHub, verify legal permissions, prove VSM function closure or certify lower cost.** Exact current GitHub readback and semantic review remain mandatory before any subsequent action.

## Ownership and stages

- The roadmap is **not** an Index reassessment, normative Profile patch or second canonical ledger.
- Existing single-harness `upstream upgrade` remains the implementation route, with material capability-delta, native tests, v2 provenance, verified matching fork and separate exact public approvals.
- Fork-local `.opensiro/contributions/<id>.json` remains **one independently implemented improvement**, on the separate `opensiro/meta` branch; a roadmap may link existing records without manufacturing a new case.
- A public original issue, comment or PR is a separate external interaction and needs a complete exact approval in the current conversation. A plan-only route has **no automatic publication**.
