# Paperclip S4=C — proposed construction and acceptance contract

**Status:** `PLAN_ONLY / DESIGN CANDIDATE`, observed 2026-11-17. **No Paperclip implementation exists in this document.** This is a reproducible engineering *target* for a possible first-party S4-specific constructor, **not a new Index score, a proven missing user demand or permission to publish an external issue/PR**. It is subordinate to [the Paperclip roadmap](paperclip-roadmap-20261117.md) and the current [Skills Methodology 0.3.8](https://github.com/opensiro/vsm-harness-skills/blob/main/skills/assess-vsm-harness/references/autonomy-states.md).

## 1. System, evidence and counterfactual

An uninstalled plugin, provider agent, private Cloud router or the Paperclip OSS maintainer organization does not supply ownership by default.
- **Accepted Index baseline:** [Paperclip canonical reassessment](https://github.com/opensiro/vsm-harness-index/blob/975a58814b767cfca414c152480f787bfe80944b/assessments/pa/paperclip.md), source `7f9867895c4e7e9589b233a93aa9efceb0c992d0`, `S4=—`. - **Native issue / strongest overlap:** [#20848 — model-release notifications and compatibility-aware upgrade recommendations](https://github.com/paperclipai/paperclip/issues/20848), observed OPEN. Compare current catalog work [#16658](https://github.com/paperclipai/paperclip/issues/16658), protected settings [#10125](https://github.com/paperclipai/paperclip/issues/10125) and any later merged equivalent before proposing new code.
- **Existing first-party boundaries:** [CEO heartbeat](https://github.com/paperclipai/paperclip/blob/7f9867895c4e7e9589b233a93aa9efceb0c992d0/server/src/onboarding-assets/ceo/HEARTBEAT.md), [company core concepts](https://github.com/paperclipai/paperclip/blob/7f9867895c4e7e9589b233a93aa9efceb0c992d0/docs/start/core-concepts.md), [approval routes](https://github.com/paperclipai/paperclip/blob/7f9867895c4e7e9589b233a93aa9efceb0c992d0/server/src/routes/approvals.ts), [AI connection router host](https://github.com/paperclipai/paperclip/blob/7f9867895c4e7e9589b233a93aa9efceb0c992d0/server/src/services/ai-connection-router.ts). - **User-level unmet task to verify:** a company operator wants to consider an *external future change* (new/retired model + changed execution-compatibility/price), compare future operating options, delegate bounded analysis to an agent, and know that an accepted recommendation actually changed the next eligible operating run without affecting unapproved current tasks. **This is an engineering hypothesis until supported by native user evidence.**
- **Simplest existing alternative:** operator checks official release notes, inspects actual agent/adapter versions and eligible accounts, manually edits a compatible model setting and checks the next run. If this is sufficient, choose `NO_USEFUL_CHANGE` rather than adding a framework.

## 2. Functional witness required for a positive S4 constructor

A proposed `S4=C` mapping requires **all** of the following first-party reachable capabilities, not merely a code module named “adaptation”:

| Link in loop | Proposed required output | Owner / negative control |
| --- | --- | --- |
| External and prospective observation | A dated, source-attributed model availability/deprecation/capability signal relevant to an actually configured company agent | Polling/storage are deterministic; release-note ingestion alone is not S4 |
| Model present vs possible future | At least **hold** and **candidate change** options, grounded in a snapshot of current agent configuration, adapter/client compatibility, eligible account, budget, reviewer role and predicted future-run impact; unknowns explicit | Internal task scheduling or a new-model notification alone is not prospective option formation |
| Decisive S4 decision/feedback constructor | A **function-specific first-party decision port** by which a developer can compose a real autonomous evaluator/agent and bind a bounded organization-level option-selection right | The composed actor owns choosing between options; generic event hooks or a human-only button do not establish autonomous `C` |
| Authorized selection | Persisted option choice (including reject/defer/hold), decision principal, policy/approval evidence, concurrency generation and reason | An evaluator cannot mint S5 authority; board/parent retains reserved policy approval |
| Return to S3/present capability | Controlled **future-run-only** configuration stage/commit, or another concrete first-party company-capability revision, with actual effective-state/next-run receipt and failure feedback | A recommendation in a dashboard, an unexecuted ticket, or a test mock with no first-party return path is not closure |

**Owner counterfactual:** with a configured evaluator removed, the first-party interface still exposes a meaningful S4-specific choose/authorize/return path, but it cannot independently exercise autonomous option-selection judgment. With the developer-composed agent connected, its different decisions must lead to different authorized later company states through that same path. If the core itself selects and closes the function autonomously, examine `A`; if only a legitimate human parent closes a function-specific loop and no autonomous constructor is supported, examine `P`. A separate closed parent S4 mode might justify `C(P)`, **never** simply because a board can approve an ordinary configuration edit.

## 3. Proposed minimal first-party ports (names illustrative, NOT existing endpoints)

A *thin* slice may implement the following contracts using current Paperclip type/authorization/concurrency conventions; these logical names are proposals, not assertions about current routes, files or stable APIs.

1. **`ReleaseSignalSource`**: import a verified provider release/change record with `companyId`, `provider`, `currentModelId`, `candidateModelId`, `sourceUrl`, `sourceObservedAt`, `effectiveAt`, `sourceDigest` and `idempotencyKey`. A test fixture or operator-imported official manifest is enough for the first slice; a live poller may be optional. Store provenance, never treat an unverified provider listing as account entitlement.
2. **`S4AdaptationCaseStore`**: persist `caseId`, source event revision, affected company/agent IDs, current configuration revisions, an environment snapshot, predicted differences, *at least hold and test/stage alternatives*, capability/price evidence, known/unknown/blocked compatibility and expiry. Distinguish `observation` → `options-ready` → `decision-pending` → `accepted/rejected/stale`; cap fanout/deduplicate by source/model/company.
3. **`S4DecisionPort`**: expose an explicit, company-scoped `evaluateAdaptationCase(caseId, snapshot)` / `submitAdaptationDecision(caseId, choice, actor, expectedVersion, reason)` path **for a configured autonomous agent actor**. The developer composes its model/authority within the existing Paperclip agent/harness contract. The core validates principal, delegated decision scope, idempotency and version but does **not** fabricate the substantive S4 option choice.
4. **`FutureRunCapabilityBridge`**: accept only an authorized **staged future-use** change after compatibility, reserved board approvals and concurrency checks. It must not silently rewrite an active run, agent's unrelated configuration, independent reviewer binding, credentials, shared access or budgets. Capture before/after configuration revision; reject stale proposals and revoked rights. A safe manual approval may be a gating policy, but is not evidence of an autonomous `C` owner.
5. **`S3ReturnAndObservation`**: attach an immutable decision→staged-revision→next-eligible-run reference. Confirm which model/config was *actually resolved* for that run, feed success/denial/fallback to the current company/CEO management view, and let the authorized owner hold/revise/revert a future-use choice. “Queued change” alone is not sufficient feedback.

**Implementation boundary:** a generic MCP connection, webhook, task list, arbitrary callback registration, model catalog or `Ask first` permission is only supporting machinery. To count toward `C`, the *shipped first-party distribution* must expose an intentionally S4-specific constructor path and an example showing a developer-composed agent actually selecting a future-oriented adaptation option and receiving closure into later company operation. It may be opt-in, but its relevant host/bridge pieces must be real and reachable without proprietary unseen services.

## 4. Ordered acceptance scenarios / release gates

Each case is deterministic, runs against a **pinned Paperclip source revision**, includes a before/after expected state and records a native test or reproducible runner trace. A mock provider release catalog, test company and non-secret compatible adapter fixture may replace live paid model accounts.

| ID | Input / decision | Required observable result |
| --- | --- | --- |
| `AC-01` External change | Official-model fixture announces a new successor used by an agent | One provenance-pinned case, source/time/affected agents, **hold** and **candidate** alternatives; stable dedup on repeated polling |
| `AC-02` Future/current coupling | Model option available but installed CLI version or account eligibility is unknown/incompatible | Case marks **unknown/blocked**; cannot claim ready-to-apply or execute the option |
| `AC-03` Actual constructor | Connect one real first-party company agent to the S4-specific decision port; feed same case under two controlled future scenarios | Agent-owned choice changes option receipt (hold vs stage); actor/principal, scope and reason are attributed; external decision logic remains developer-composable |
| `AC-04` Return into present capability | Authorized choice selects compatible candidate after required approval | Version-guarded future-use configuration change is staged; next **eligible** agent run uses expected resolution and returns a linked observation receipt; current run stays pinned |
| `AC-05` S5 reserved rights | Agent has S4 option-selection rights but not ultimate company policy or model-change approval rights | Without required approval, result stays pending/denied; no silent S5 transfer, new credential, grant, purchase or budget expansion |
| `AC-06` Wrong actor | Other company/agent/user attempts to submit or apply a case | Cross-company and unauthorized decisions fail closed; no state mutation and no leaked model/account data |
| `AC-07` Concurrency and revocation | Submitted against outdated agent config, removed account, expired signal or revoked delegated rights | Conflicting case rejects with reason; no change to protected config, reviewer selection or active sessions |
| `AC-08` Refusal/deferral | Configured actor chooses hold or authorized board rejects | Durable reason and suppression/snooze rule; no future-run change and no duplicate notifications for the same source revision |
| `AC-09` Negative S4 witness | Only notification, release notes, eval memory, plain job queue or human button is active | Test confirms **no autonomous constructor claim** from these components alone; labels stay `support/possible P`, never asserted `C` |
| `AC-10` Failure feedback | A staged model becomes unavailable at the next run or a canary fails | Failure is surfaced to S3/owner, with bounded stop/revert where provided; no silent repeated upgrade or lost decision provenance |

**Native quality gates:** no credentials in fixtures; all new permissions map to existing role/company boundaries; source-verified compatibility checks; no control-plane bypass; robust idempotency/cancellation; audit with source and actor; unchanged ordinary agent/review/approval behavior. The first slice can defer sophisticated canary dashboards, ML ranking or many-provider polling, **not** the function-specific ownership/feedback path.

## 5. Engineering sequence and evidence for Index re-review

- **P0 — demand and dedup:** compare the full current first-party mode, issue #20848 and any competing implementation diff; show a current user task that manual settings cannot handle sufficiently well. If no credible user value, end `NO_USEFUL_CHANGE`.
- **P1 — smallest usable vertical slice:** import a trusted single-provider signal → persist two options and compatibility state → configure one first-party autonomous evaluator via S4 decision port → authorized future-use config stage → next-run actual-state receipt/feedback. Implement as a supported optional feature if that fits the original product better than a global controller. Tests `AC-01` through `AC-09` (plus safety aspects of `AC-10`) are mandatory for a `C` target. “Notification only” may be useful as a **product** contribution but cannot be described as a completed `C` constructor.
- **P2 — optional enhancement after demand:** live provider polling, better diff/cost projections, canary and rollback UX, multiple adapter backends, proactive retirement support; measure costs and avoid duplicate control surfaces.
- **Publication:** any actual product code requires the existing `upstream upgrade` functional-delta, native-test, verified fork, license/contributor/AI disclosure, fork-local review and separate external-publication gates. Plan-only has no permission to open a Paperclip issue/comment/PR or a public fork-local PR.
- **Reassessment gate:** only after code really ships at a newly pinned source ref, an **Index-owned fresh source-first review** may decide whether `S4=C` (or another state) is supported. The engineering tests prove a product feature; they are **not** an automatic grade or independent S4 semantic proof.
- **Cost hypothesis:** compare matched operator-run migration task against manual-native workflow with implementation/integration/testing, maintenance effort, actual future-run success, error and rollback safety. **Cost status: NOT_MEASURED**.

## 6. Decisions still open

- Is this desired as a first-party optional company feature or a plugin with a **genuinely first-party S4-specific host bridge**? A generic uninstalled plugin cannot independently establish `C`.
- What source is authoritative for model availability **and** actual adapter/account eligibility, and who may authorize each company-level configuration class?
- Is an autonomous evaluator a realistic product user need, or is board-only review sufficient (`P` candidate, not automatically `C`)? This must be resolved by source-native operator evidence rather than a target grade.
- Which single future-use setting can be changed safely without altering reviewer independence, current sessions, provider account access or budget policy?

**Stop condition:** if any essential `C` witness (externally prospective input, structured options, developer-composable decisive actor, authorized first-party return or observed later-use feedback) cannot be made source-native and testable, record the unresolved condition and choose `NEEDS_EVIDENCE` or a smaller feature rather than calling a notification feature `S4=C`.
