# External contribution publication waves

**Owner:** Upstream Contributions, under [Upstream #6](https://github.com/opensiro/upstream/issues/6) and [#56](https://github.com/opensiro/upstream/issues/56). This is an operator grouping rule for existing contribution handoffs, **not** a new source-screening command, external-PR grant or adoption metric. The independent, [standing preparation mandate](STANDING_PREPARATION_AUTONOMY.md) now authorizes qualifying fork/patch preparation in five-source waves without per-stage owner prompts; it is not an external-PR publication grant or proof of live executor capabilities.

## Wave contract

When the operator requests external contributions in waves, select **five distinct third-party repositories per wave** from existing source-pinned technical handoffs. Count repositories, not patches or PR URLs. Check against already published external PRs and currently active internal source claims before selection. Preserve the selected identities and their order in a five-row status/readback; do not silently substitute a convenient sixth source when a selected case is blocked.

**Working-fork-first delivery invariant:** a source-native patch intended for public review belongs on a verified `opensiro/...` branch in the **matching** `opensiro-contributions/<target>` fork, after an effective [#6](https://github.com/opensiro/upstream/issues/6) preparation-stage grant. The external PR is then composed **from that branch and its final diff**, in the third-party project's own PR format. `opensiro/upstream` retains immutable technical evidence, working-fork intent, provenance and external lifecycle readbacks; it is **not** an intermediate warehouse of copyable PR descriptions. In particular, do not open one internal Upstream PR per five sources merely to store proposed titles/bodies when no fork branch or publication operation happened.

For **each of the five**, independently:

1. Read the current upstream default branch/ref, license text, contribution/security policies, PR template and relevant issues/PRs. Distinguish a historical native test pin from the current source and check for maintainer fixes or duplicate work.
2. Review the product-native patch, matched before/after test receipts and any first-party CI gaps. If source has moved, rebase/replay and rerun relevant native tests before claiming current readiness. Do not use live LLM/agent/provider trials as a substitute for deterministic source validation.
3. **Autonomously prepare the contribution in its working fork** without per-repository human approval, under the active, revocable [standing preparation mandate](STANDING_PREPARATION_AUTONOMY.md) and fresh automatically issued bound execution decisions. Verify the authentic public parent, source/base/branch SHA, permitted branch and absence of duplicates; create or update only the verified `opensiro/...` working branch, apply code/tests, execute available native checks and read back the actual commit/diff. A `gh` login, an existing fork, the five-repo command or an offline unit test is **not** a substitute for provider/host checks. If a capable trusted executor is absent, record `WAITING_FOR_TRUSTED_EXECUTOR` and advance without asking the owner to authorize the same preparation step again or creating a stand-in PR-body document.
4. **Prepare the actual external PR from the fork diff**: read the target's latest source-native PR form and policies, fill its requested sections/checks/legal attestations truthfully, then append [AI disclosure v2](AI_ASSISTED_PR_DISCLOSURE.md) with the current and historical canonical Index URLs, original `reviewed_at` and `review_ref`. Show the specific final title/body, changed files, fork head SHA and real test receipt to the human publication owner. Do not invent passing tests, CLA/DCO consent, human code review or adoption. An older Upstream prose proposal is never a substitute for this fresh readback.
5. Obtain **specific publication approval for that exact title/body**, as required by the [prospective human-per-PR gate](CORRECTIVE_PR_PUBLICATION.md). A wave-level command is not five individual publication approvals. Publish the validated external PR as **Open · Ready for review**; use Draft only for an explicitly accepted, target-permitted readiness condition. Read back the real external PR, register its actual URL/head in the applicable reviewed ledger/watchlist, and maintain CI and maintainer feedback. Never merge into third-party repositories.

Return a **five-row operator status even when zero PRs can be published**. Each row states source ref, license/policy or test gap, working-fork branch status, exact permission state, source-linked disposition and next allowed action. Persist a reviewable Upstream record **when material source evidence, a registry entry or an attributable external action actually changes**; otherwise an operator status/owning-issue update suffices. Do **not** create a docs-only internal PR just to repeat five blocked dispositions or park unapproved target PR prose. Blocks stay attached to their original case; resuming them requires the missing evidence/authority. A subsequent wave selects another five distinct candidates without declaring blocked cases rejected or successful.

The technical [`upstream batch` / `upstream upgrade batch`](ASSESSMENT_CANDIDATE_BATCHES.md) five-source screening cohorts remain separate: a screening outcome of `AWAITING_EXTERNAL` is a prepared hypothesis/patch, **not** publication approval. The existing [Upstream Auto](UPSTREAM_AUTO.md) task-reservation prototype does not issue five publication grants or spawn agents.
