## Control Plane command: `batch upstream`

This is the first-class **technical contribution batch** entry, not the Index command `start a batch assessment`, the read-only `contribute to other harnesses` shortlist or an autonomy-evaluation run. The operator has selected Upstream #56 as the work lane. Execute already-authorized technical stages to their actual boundary without asking for a second candidate-selection decision.

- **Reconcile before allocation:** refresh the current main and open PRs in Upstream and Index, existing batch manifests and source refs; include unmerged draft cohorts as **occupied** to avoid races with parallel agents. Do not seize another actor's active or frozen row, duplicate a source, silently re-pin an assessment, or change a cross-repository `TODO.md` schedule. Use the existing batch manifest and owner PR; do not start a competing copy.
- **Freeze a full cohort:** if no unresolved eligible row exists, take **five distinct** eligible included Index assessment records on one exact canonical Index commit, exclude prior batches and concurrent reservations, record evidence paths and upstream refs, and validate the manifest before the first source intervention. An exceptional 6–10-row cohort requires an explicit operator number; fewer than five verified eligible records is `NO_ELIGIBLE_ASSESSMENT_CANDIDATE`, not a shortened batch. An assessment grade alone never establishes a bug.
- **Apply the native technical loop:** screen rows **serially** with `need`, `mechanism`, `counterfactual` and `scope` fit gates; investigate actual upstream source/overlap and licenses, validate reproducible **before/after native deterministic first-party regression tests** on pinned genuine source when fit passes, prepare a minimal patch and attributable handoff; record `CLOSED_NO_CHANGE` or `BLOCKED_EVIDENCE` when proof fails. For **new strict `ASSESSMENT_DERIVED`** cases, first checkpoint the assessment-origin hypothesis *before* fresh source/issue inspection, then have a **separate deterministic runner/CI** execute the native tests and preserve run receipts; the chatbot must not itself run validation. Follow [the assessment-derived validation boundary](ASSESSMENT_TO_IMPROVEMENT.md#pre-registered-hypothesis-and-separate-native-execution--2026-11-08-refinement) and [native CI placement](NATIVE_CI_EXECUTION.md). No live LLM agents, model providers, Browser quality trials, fabricated positive checks or unfounded feature promises.
- **Separate publication:** an internal reviewable OpenSiro patch/PR is a technical return, not an external submission. Without a separate effective external fork/branch/PR-stage grant, mark qualified packets `AWAITING_EXTERNAL` and **advance to the next row**. The historical finite 34-case Corrective mandate does not apply to this new cohort. Only external provider receipts and maintainer decisions can close external delivery; don't conflate screening completion with accepted contribution.
- **Finish and resume:** run `python3 scripts/assessment_candidate_batches.py validate|status|next <manifest> --index-root <exact-pinned-index-checkout>` using the individual valid subcommand syntax; publish a reviewable five-row summary with refs and blockers. `NO_ACTIONABLE_CANDIDATE` means this frozen *screening* cohort is exhausted. Start the next full, source-disjoint cohort only after the prior review/integration and a fresh concurrent-work check.

## Control Plane command: `upstream upgrade batch`

This is the **second technical batch command** within the existing Upstream S1/#56 workflow. It shares the current five-source intake, duplicate/reservation checks, serial progression, native-fit gates, internal PR handoffs and external-publication boundaries with `upstream batch`; it does **not** create a new scheduler, executor, authority envelope or competing queue.

Both batch commands search for **possible VSM-grounded product hypotheses** when examining canonical Index assessments. The difference is how they select and attribute interventions:

| Command | Assessment hypothesis search | Technical selection |
| --- | --- | --- |
| `upstream batch` (legacy `batch upstream`) | Inspect the pinned assessment's relevant function/owner/closure evidence; record a falsifiable possible weakness or an honest `CLOSED_NO_CHANGE` screen. | Useful first-party technical fixes may remain `ASSESSMENT_INFORMED`; never inflate the derived label. |
| `upstream upgrade batch` | **Prioritize prospectively `ASSESSMENT_DERIVED`** functional/ownership/feedback hypotheses and record the predicted weakness, null case and falsifier **before** fresh upstream code/issue inspection. | Pursue a change only if independent first-party native need/fit and safe counterfactual benefit pass. A `C → A` grade change is **not** required or promised. |

For the explicit `upstream upgrade batch` request:

1. Reconcile the current shared Upstream/Index cohorts, open PRs and source claims. Resume an already selected **upgrade-mode** cohort, if any; otherwise freeze **five** distinct, available included Index assessments on one immutable Index commit. The cohort contains five *questions*, not five pre-approved patches or five proven derived findings.
2. Before inspecting current target implementation/issues, checkpoint an assessment-based finding → predicted product-native weakness → expected benefit → null/falsifier and attributable time/ref for each plausible hypothesis. An assessment with no supported hypothesis records a transparent negative screen; do not invent one from a low `C` label.
3. Independently inspect first-party code, maintainer needs, contributor policy and the `need / mechanism / counterfactual / scope` gates. Reject unsafe, undesired, already fixed or unsupported changes. A later issue-discovered defect is `ASSESSMENT_INFORMED` and belongs to ordinary `upstream batch` work, **not** this mode's derived-benefit numerator.
4. For admitted strict-derived cases, prepare the minimal native patch/test, but have a **distinct deterministic CI/runner** execute pinned matched before/after source-native tests; retain run identity, source/test hashes and logs. The chatbot must not directly execute those tests as validator. Missing runner is `BLOCKED_INDEPENDENT_EXECUTION`, not `BENEFIT_SUPPORTED`. No live LLM/provider/Browser quality trials.
5. Report all **five** row outcomes, including `CLOSED_NO_CHANGE`, `BLOCKED_EVIDENCE`, `NO_BENEFIT_OBSERVED` and independently supported benefits. Separate the number screened, prospective derived hypotheses, confirmed native needs, verified benefits, informed-only findings and external PR lifecycle. A prepared internal fix is not external acceptance; publication rights remain separately gated.

Use the existing [assessment-to-improvement origin/validation contract](ASSESSMENT_TO_IMPROVEMENT.md) and per-candidate manifest controls. Identify the requested mode in its controller/summary without adding unvalidated fields to the frozen JSON schema. **Do not repin existing cohorts, create concurrent duplicate batches, or reinterpret historical records.** This absorbs the design question previously routed through [Organization #307](https://github.com/opensiro/vsm-oss-organization/issues/307); there is no separate active `batch upgrade` command.

## Meaning of `continue` / `продолжай` / `המשך`

Within this expressly selected **#56 experiment** and its explicitly chosen `upstream batch` or `upstream upgrade batch` mode, these commands mean: **complete the furthest currently allowed step for the current candidate, record the actual result and proceed to the next eligible row without asking for another scheduling decision**. They do *not* mean repeating a completed package, selecting an arbitrary GitHub issue, waiting at a candidate's external authorization gate, or starting model-agent trials.

1. **Bootstrap:** refresh VSM-OSS `START_HERE.md`, the current Index, this repository's default branch, #56 and #6. Use the **already frozen batch** unless the whole batch is resolved; never silently re-pin historical assessment identities.
2. **Freeze intake before execution:** select a bounded, full cohort (normally **five** assessment records, up to ten) from the canonical *included* Index corpus. Record one exact Index SHA, each assessment path, assessed upstream repo/ref, source-derived question and fixed order. For prospective `ASSESSMENT_DERIVED`, commit or otherwise timestamp the predicted native weakness, expected benefit and null/falsifier **before** investigating the target's fresh code/issues; a later VSM explanation is not derived-origin evidence. Check for duplicate prior candidates/interventions. This is a **screening cohort**, *not* a claim that five useful patches are known or that five S1 work items are admitted. Never pad with unassessed GitHub favourites.
3. **Screen in order:** for the first `SCREENING` or `ACTIVE` row, independently inspect current upstream source, issue/PR overlap, policy/licensing and native tests; record the four fit gates (`need`, `mechanism`, `counterfactual`, `scope`) and dated primary-source links. A VSM grade alone is not a bug. If fit fails, `CLOSED_NO_CHANGE` with evidence; if insufficient, `BLOCKED_EVIDENCE` with the missing input.
4. **Execute a qualified case:** only after four `PASS` gates and a falsifiable source-derived plan, require relevant **native deterministic scripts** against pinned genuine product code, matched baseline/after and controls. For prospective strict-derived cases, dispatch them to a distinct CI/runner and verify its first-party source/test pins, run URL, commands, logs and controls; when unavailable record `BLOCKED_INDEPENDENT_EXECUTION`, not a chatbot-executed benefit claim. **Never** run live LLM agents, Browser quality trials or provider calls for this experiment. Track origin class separately (`ASSESSMENT_DERIVED`, `ASSESSMENT_INFORMED`, `GENERAL_UPSTREAM`, `INSUFFICIENT`) and never retroactively improve it.
5. **Return then advance:** when a valid local test/patch/handoff is complete and external fork/PR authority is unavailable, mark **`AWAITING_EXTERNAL`** with the precise prepared packet and unexercised right, then immediately continue to the **next** eligible row. `AWAITING_EXTERNAL` is **not** a closed contribution, not a denial and not evidence of external delivery. Revisit it only after a new, attributable grant, a fresh maintainer response, or an explicit targeted command. A genuine unresolvable policy conflict may end in `ESCALATED`, without blocking unrelated candidate screening.
6. **Batch rollover:** only when no eligible rows remain, produce an evidence-backed batch summary and select the next **complete** frozen cohort from fresh canonical Index evidence. Do not reinsert screened or deferred candidates into the new batch without an explicit, documented revisit decision. If there are insufficient eligible assessments, state `NO_ELIGIBLE_ASSESSMENT_CANDIDATE` without a manufactured batch.

The row lifecycle is `SCREENING → ACTIVE → AWAITING_EXTERNAL` (or `CLOSED_CHANGE`/`CLOSED_NO_CHANGE`/`BLOCKED_EVIDENCE`/`ESCALATED`). A screening row is **not admitted** until native fit succeeds. A prepared local packet can close its bounded *technical step* while the external contribution remains pending; report these distinctly. The ordering is deliberately **serial** for auditability; no new scheduler, reviewer agent or daemon is introduced.

The command never grants permission, mutates files, contacts GitHub or picks a new assessment cohort itself.
