This document belongs to Upstream; it is not a new batch, source reservation, assessment method, executor or grant of authority.

## Why change the research question?

The [batch 39 diagnosis](https://github.com/opensiro/upstream/pull/301) reports 50/60 unsupported preregistered function hypotheses and 9/10 feature questions with `need` and `counterfactual` pending. The ongoing [batch 40 investigation #303](https://github.com/opensiro/upstream/pull/303) and [batch 37 revisit #304](https://github.com/opensiro/upstream/pull/304) have valuable source-native evidence, but much of the effort concerns SDK compatibility, idempotency, retry failures and other **repair/reliability** matters. Those tests alone do not establish that a new useful product capability was conceived, tested or delivered. Do not treat either open PR as merged.

## The capability contract: answer before extended testing

Describe one priority opportunity in existing research prose, without new manifest fields or per-rule IDs:

1. **Who needs it?** Identify an original-repo user/operator, first-party maintainer request or precisely labeled unconfirmed Index-first prediction.
2. **What NEW task can be done?** Specify trigger → observable action or decision → output/API. Name the exact original-version capability, if any, that performs a similar task.
3. **Why is the result useful?** Define a reproducible benefit proxy: newly completed task, better evidence discrimination, meaningful operator decision, coverage/cost/time under a bounded first-party fixture. Provide a negative/compatibility control, not an invented adoption claim.
4. **What VSM mechanism suggests the opportunity?** Cite relevant function, current decisive owner, closure/feedback evidence and source/assessment boundary. A blank or low A/C/P state is **not** proof of product need.
5. **What needs to be decided?** Source-native no-feature baseline, competing PR, maintainer contract/RFC, required compatibility and smallest decisive native test or design answer. Mark still-missing evidence as pending.

**Classification by new user capability, not code shape:** `MINOR_FEATURE`/`MAJOR_FEATURE` means a new independently useful workflow, supported host/provider integration or operator decision output. Fixing a broken current workflow, retry/idempotency contract, SDK version mismatch, refactor or extra regression test is `BUG_FIX` / reliability fallback unless a *separately demanded* new user task/decision was established. A reliability fix is not automatically a feature. A missing source API alone is not value; equally, a new recovery decision workflow can count as a feature if its separate user-facing contract is evidenced.

## Research and decision flow

1. **Preserve origin chronology and six-function coverage.** Strict `ASSESSMENT_DERIVED` features require a frozen Index-only prediction before examining fresh original source/issues. A maintainer-driven `SOURCE_FIRST` feature is `ASSESSMENT_INFORMED` or `GENERAL_UPSTREAM`, not retroactively VSM-derived. Keep original source reservation and owner.
2. **Try one decisive product-native comparison.** Confirm existing workflow, hypothesized novel user action and counterfactual. Before-to-after scripted native fixtures should show a real new action/output, with matched inputs and negative/compatibility control. A mock-injected failure, syntax check or missing-method test alone does **not** demonstrate capability value. Do not require or initiate live LLM/model/browser/user trials under #56; all native quality claims remain bounded to scripted fixtures.
3. **Retain all admission gates.** `need/mechanism/counterfactual/scope = PASS` before derivative implementation, source license/rights/maintainer design, and a separate deterministic runner for strict-derived before/after validation. Exploratory source probes may continue with pending fit; their results are not implementation authorization.
4. **Stop intelligently.** If the user contract or maintainer design decision is missing, keep `OPPORTUNITY_RESEARCH_PENDING` with an owner and the smallest next decision. Stop repeated reliability detours for that feature. A supported repair can proceed separately in the ordinary upstream lane; report it as `BUG_FIX`, **not** a new capability or strict-derived success. A source-proven duplicate can close only its bounded claim as `CLOSED_NO_CHANGE`; unknown is not negative proof.
5. **Report separately:** (a) new-capability hypotheses and grounded benefit comparisons, (b) reliability/repair findings, (c) existing/duplicate features. Six-function source scans are `SCREENING_COMPLETE`, **not** `OPPORTUNITY_DECIDED` or proof that all native features have been exhaustively evaluated. Preserve original product-effect, maintainer acceptance and user-adoption distinctions.

## Three prospective, source-first examples (not admitted improvements)

- **[Akmatori #67](https://github.com/akmatori/akmatori/issues/67):** new read-only cross-incident evidence *decision* for an operator: show two independent supporting incident claims, one contradictory incident, provenance and repeat-incident control. Do **not** auto-promote trust/confirmation. Need for eventual corroboration is discussed; user output contract, scope, native counterfactual and owner approval remain pending. This is not already an assessment-derived VSM finding.
- **[srchd #204](https://github.com/dust-tt/srchd/issues/204):** supported demand for selectable search providers / scientific retrieval. Respect existing contributor [PR #203](https://github.com/dust-tt/srchd/pull/203) and maintainer discussion of `browse`. A Firecrawl SDK type-contract mismatch is a **repair finding**, not a provider feature. First compare bounded biomedical/patent query coverage, valid links, citation contract and parity/cost; no duplicate PR.
- **[HelixHarness #11](https://github.com/didi/helixharness/issues/11):** maintainer-backed Cursor host support. Define an end-to-end user path through project init / Propose / Apply / Archive plus current Codex/Claude compatibility. A registry test is not sufficient to establish a new host workflow.

The separately open [VSM-guided autonomous improvement study #299](https://github.com/opensiro/upstream/pull/299) is a *proposal*, not an integrated autonomous S3/S4 organization or evidence of better outcomes.
