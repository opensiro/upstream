## 1. wanman — concurrent same-scope task admission

- **Index evidence:** [`assessments/wa/wanman.md`](https://github.com/opensiro/vsm-harness-index/blob/46219bf103b0b122d86abc3ca70ae3d8bc820e2c/assessments/wa/wanman.md), `chekusu/wanman@d3a8138de6c21981a4f1449a7b3f201e724c55c9`; included `S1=A, S2=C`. S2 observes supervisor RPC rejection of active overlapping task/capsule scopes via a check against current nonterminal tasks; the assessment explicitly limits this to declared scopes and notes possible concurrent admission races.
- **Prediction:** two concurrent `TASK_CREATE` calls for the same declared path could both pass overlap inspection before either assignment becomes visible, allowing duplicate active ownership.
- **Native test / intended improvement:** invoke the actual first-party supervisor admission path with two synchronized overlapping task requests, assert at most one accepted active owner; test disjoint tasks remain concurrently admissible. If a race exists, serialize or atomically reserve the check-and-create boundary, not merely add an advisory warning.
- **Null / falsifier:** a single-threaded RPC event loop, transaction, critical section, or existing atomic claim makes duplicate admission impossible, or the product explicitly scopes the guarantee to serial admissions. Avoid inventing global Git conflict safety.

## 2. Genesis Agent — skill registry across processes

- **Index evidence:** [`assessments/ge/genesis-agent.md`](https://github.com/opensiro/vsm-harness-index/blob/46219bf103b0b122d86abc3ca70ae3d8bc820e2c/assessments/ge/genesis-agent.md), `me7ko-dev/genesis-agent@0e24818a9fd0788c6fe68b2e51ba3a3083f6d2fc`; included `S1=A, S2=C`. S2 observes parallel delegated worker updates to a shared persistent `skills.json` registry protected by an in-process `_SAVE_LOCK` and atomic replacement.
- **Prediction:** if two **supported** Genesis processes share the same skill-library directory, each process-local lock may allow a stale read→replace cycle that drops the other process's newly saved skill.
- **Native test / intended improvement:** two real `save_skill` calls from separate subprocesses with a controlled barrier and distinct skill identities; verify both survive and a corrupted/partial registry never appears. A confirmed multiprocess supported mode may need file-scoped interprocess coordination and safe atomic replacement.
- **Null / falsifier:** only one process is supported per library, or current code already uses a cross-process transaction/merge with current-state reread. Do not build distributed locking for an unsupported deployment mode.
