## 1. KnowWork — sandbox ownership across service processes

- **Assessment:** [KnowWork S2=C](https://github.com/opensiro/vsm-harness-index/blob/da98a140b1c6541f639c1dc4094bf2aeaacdb08d/assessments/kn/knowwork.md), `knowflow-ai/KnowWork@83c763e4fe2d63cd59e0344268afa94321d35585`, reviewed 2026-10-24.
- **Observed assessment constraint/owner:** sandbox-enabled per-session DSH S1s use `SandboxKey(workspace_id, session_id)`, deterministic Docker name/labels and per-key locks managed by a first-party Python business service. The assessed benefit is narrow collision rejection and same-session continuity, not global arbitration.
- **Prediction:** two *independent business-service processes* on a shared Docker daemon may have independent per-key lock registries; simultaneous same-session acquire/create could both cross a local admission check and produce a spurious conflict, wrong owner adoption or duplicate creation/retry, if the Docker lifecycle is not safely idempotent across processes.
- **Desired native effect:** same-key concurrent starts converge to one correctly labeled sandbox and return safe recoverable results, without cross-workspace adoption.
- **Prespecified native falsifier:** first-party two-process same-key/container-acquire fixture using a controlled fake Docker client or a native lifecycle test; assert exactly one owner and no cross-tenant adoption. **Null:** daemon name uniqueness, label verification and retry already make cross-process starts harmless, or this deployment does not support multi-process managers → `CLOSED_NO_CHANGE`; lack of a feasible bounded native fixture → `BLOCKED_EVIDENCE`.
- **Scope:** standard sandbox-enabled deployment only; `--no-sandbox`, Docker daemon compromise and live LLM-agent trials are excluded.

## 2. CodeAgent (Harvil1) — orphaned conditional task ownership

- **Assessment:** [CodeAgent S2=C](https://github.com/opensiro/vsm-harness-index/blob/da98a140b1c6541f639c1dc4094bf2aeaacdb08d/assessments/co/codeagent-harvil1.md), `Harvil1/codeAgent@e48780be52949dfcf17338025f6beab48ca01428`, reviewed 2026-10-15.
- **Observed assessment constraint/owner:** cross-process conditional `TaskStore.claim` plus `CODEAGENT_KANBAN_TASK` worker binding enforce a single assigned owner. Parent model retains the discretionary rescope decision; constructor holds task claim coordination.
- **Prediction:** if a claimed worker dies abruptly before normal cleanup, the durable task may remain exclusively claimed and a supported replacement assignment may be unable to recover despite no surviving S1 owner; unsafe unconditional reclaim would conversely admit duplicate writers.
- **Desired native effect:** a bounded, first-party replacement or explicit recovery path preserves at-most-one live owner while permitting restart after verified terminal loss.
- **Prespecified native falsifier:** persisted TaskStore + coordinator fixture that claims for worker A, simulates documented worker termination, attempts reassignment to B; check stale-claim release and concurrent A/B exclusion. **Null:** current first-party lifecycle has safe timeout/reclaim, or recovery intentionally requires an explicit human control not supplied by the product → no speculative automatic reclaim.
- **Scope:** shipped task/team worker mode, not file/worktree collision prevention or arbitrary OS crash recovery guarantees.

## 3. Cloud Coding Agent Node — simultaneous same-tenant start idempotence

- **Assessment:** [Cloud Coding Agent Node S2=C](https://github.com/opensiro/vsm-harness-index/blob/da98a140b1c6541f639c1dc4094bf2aeaacdb08d/assessments/cl/cloud-coding-agent-node.md), `fred1433/cloud-coding-agent-node@a6758498055b54d765f6ca3423c58c67e0ead18e`, reviewed 2026-10-02.
- **Observed assessment constraint/owner:** `NodeService` namespaces runs by `(tenant, run_id)`, has a service lock and per-run sandbox IDs. Existing contract covers two tenants with same public `run_id`.
- **Prediction:** same-tenant *simultaneous* starts of the same run identity, not merely sequential retries, might race at lookup/creation and run two S1 loops before the registry stores a winner, unless admission is atomic over the async task boundary.
- **Desired native effect:** one native runner execution and one identity regardless of overlapping duplicate `start` requests; different tenants stay isolated.
- **Prespecified native falsifier:** an async barrier-controlled first-party `NodeService.start` fixture invoking two requests for identical `(tenant,run_id)` and counting actual task launches, with a different-tenant control. **Null:** the current lock already fully encloses check/insert or the API admits only serialized callers → `CLOSED_NO_CHANGE`.
- **Scope:** one supported `NodeService` instance; no claim of distributed Kubernetes coordination or model/provider quality.

## 4. Polyphemus — ambiguous tool-call identity during stitched interleaving

- **Assessment:** [Polyphemus S2=C](https://github.com/opensiro/vsm-harness-index/blob/da98a140b1c6541f639c1dc4094bf2aeaacdb08d/assessments/po/polyphemus.md), `polyphemus-ai/release-rehearsal@02020f3bc2829c350fd726273a7721254068925f`, reviewed 2026-09-28.
- **Observed assessment constraint/owner:** concurrently addressed model-tool S1s share a thread; first-party `stitchHistory` repairs interrupted call/result adjacency and resynchronizes later runtimes.
- **Prediction:** distinct simultaneous agent turns may reuse a provider-local tool-call ID; stitching by ID without an adequate turn/agent scope could attach a peer's result to the wrong call when histories interleave.
- **Desired native effect:** call/result alignment remains correct under repeated IDs from different agent turns, or the runtime explicitly rejects an ambiguous history rather than silently attributing a result.
- **Prespecified native falsifier:** deterministic first-party `stitchHistory` unit fixture with two explicitly distinct agent turns and colliding call IDs plus valid peer interleaving; assert pairing and retained peer material. **Null:** IDs are globally unique by contract, caller scopes disambiguate them or the stitcher already handles duplicates deterministically → `CLOSED_NO_CHANGE`.
- **Scope:** shipped history reconstruction only; no live model, external integrations, shared-thread policy changes or inferred autonomous S2.
