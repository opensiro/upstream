# v0.15.0 — Popularity-first Upgrade selection, chat-native batch reports

**Prospective MINOR; 2026-11-16.** This package changes operating priorities and operator reporting; it does not add a new code runner, record schema, external authority, repository or metric.

## Default priority and distribution

1. Rank eligible **original** target harnesses by observed number of unique GitHub contributors. When unavailable, use original-repository stars as a clearly labeled fallback rather than pretending stars are contributors. A specified target always overrides default ranking.
2. Give one researched opportunity to each distinct eligible source in descending popularity order before repeating sources. Then prefer additional justified opportunities using a modest linear rank-percentile weight from 1× to 2×, or use explicitly requested `uniform` round-robin. This is a **research selection preference**, not a target PR/contribution rate, fixed quota or evidence of product demand.
3. Use existing independent OpenSiro contribution IDs to see where we already worked; do not count replacement PRs or batch appearances as additional contributions. Require genuine independently evidenced user need before any further implementation.

## No per-batch GitHub bookkeeping

`upstream upgrade batch N` and `upstream batch N` run as chat-level bounded investigation and report: N distinct original sources (or exact shortage), evidence/provenance links and source revisions, popularity observation, six-function dispositions where upgrade mode requires them, feature-vs-repair results, native evidence and next action. No new issue, PR, cohort manifest, branch, scheduler or metadata event solely to represent a batch. A meaningful newly authorized engineering intervention still has a single canonical fork-local `.opensiro/` contribution record and attributable significant events under existing gates.

## Reuse rather than rebuild

Historical v0.8.0–v0.9.0 contracts already introduced multifunction opportunity depth, capability-first native comparison, evidence classification, four native-fit gates and independent deterministic runner requirements for strict assessment-derived evidence. v0.11.0 required early working-fork handoff; source-matched fork CI and actual bounded external PR chains exist. These receipts are retained historically, **not** proof that a generic v0.15.0 autonomous CLI Upgrade runner has been built or fully tested.

Exact-source/native checks, permissions, `DORMANT / PAUSE / STOP` and per-action third-party public consent remain unchanged. No automatic release or tag is implied.
