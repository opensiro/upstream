# Upstream contribution protocol — v0.16.0

[Home](README.md) · [Fork-local records](docs/FORK_METADATA.md) · [Architecture](docs/ARCHITECTURE.md) · [Historical migration #2](https://github.com/opensiro/upstream/issues/2)

**One harness may have many independent improvements. The detailed operational state belongs to its verified working fork, not a pile of permanent Upstream issues.** No fixed maintenance TTL is imposed. Upstream is an existing S1 domain of OpenSiro VSM OSS, not a second organizational control plane.

## Ownership and work unit

Before a real fork exists, Upstream may own one **minimal intake issue** containing a real source identity, open decision and evidence links; source-proven negative findings need no invented fork or patch. Once a correct [opensiro-contributions](https://github.com/opensiro-contributions) fork is verified, use `.opensiro/` on its independent `opensiro/meta` branch as the **canonical local state and attributed decision/event history** for all that harness's contributions. One `contributions/<stable-id>.json` = one independently scoped useful improvement/repair, not an issue, chat session, old batch, external PR or mandatory new issue. An Upstream issue may remain as a link/operator task, never an authoritative duplicate mutable ledger.

Read [docs/FORK_METADATA.md](docs/FORK_METADATA.md) for the initial JSON contract and authority/branch rules. The original GitHub repository alone owns the actual external PR's open/merge/closure/reviews. Upstream only shows source-linked dated projections.

**External maintainer issue watching:** when an upstream product or PR-admission decision is awaiting source review and no external PR exists, use [fork-local, source-linked `issue_watch`](docs/ISSUE_WATCHING.md) in the *existing* stable contribution, not a new issue/PR ledger or invented `work_state`. Observe original issues/comments/labels with bounded readback and durable cursor-based dedup; never infer publication consent. The watcher is on-demand by default and scheduled only by an explicit opt-in variable and fork-scoped credential. It cannot auto-publish third-party PRs.

## Research and qualification

1. **Before popularity ranking, capability scoring or deep research**, pin the original source identity/revision and perform the read-only [license-and-formalities preflight](#license-and-formalities-first--human-gate-category), followed by the [autonomy preflight](#autonomy-preflight--before-capability-ranking-and-source-selection). Then check existing behavior, competing PRs and prior evidence links including [upstream-old](https://github.com/opensiro/upstream-old); legal/authority uncertainty is not permission.
2. Ask **who needs what NEW task/output and why**, or which existing behavior is demonstrably broken. Propose a bounded benefit proxy and original alternative. A retry fix remains a repair unless a new feature is independently supported.
3. Respect provenance order: `ASSESSMENT_DERIVED` requires an earlier dated and pinned Index-first prediction; `ASSESSMENT_INFORMED`, `GENERAL_UPSTREAM` and `INSUFFICIENT` must not be misrepresented as causal VSM improvements. **Persist this classification in every new fork-local contribution record** (`schema_version: 2`, `contribution_type`, rationale and evidence URLs); run the source-native validator before writing `opensiro/meta`. A “VSM_DERIVED” nickname maps to the existing `ASSESSMENT_DERIVED` evidence gate; do not invent a second taxonomy. Never treat missing legacy classification as `GENERAL_UPSTREAM` or `ASSESSMENT_DERIVED`; report `UNCLASSIFIED_LEGACY` until independently reviewed. See [fork metadata](docs/FORK_METADATA.md#mandatory-contribution-origin-new-records-schema-v2).
4. Check native **need, mechanism, counterfactual and scope**. Unsupported claims remain pending. No mandatory six-function S1–S5 scan or per-session batch.
5. Before implementation, apply the [material capability-delta gate](#material-capability-delta-gate-before-implementation). An Index link, a new configuration flag, a passing unit test or an absence in a VSM function vector is not independently a useful Upgrade.

## Capability-first `upstream upgrade` (new work, not historical batching)

These are **conversational operator routes**, not shell commands, a new scheduler, a frozen-batch producer, or automatic authority to write to forks. Their purpose is to find a **real new user/operator task or decision** that an agent harness cannot currently perform, explain why a VSM mechanism is a useful hypothesis for that need, and then independently test the smallest native improvement. Use the current [fork-local metadata](docs/FORK_METADATA.md) and [read-only aggregator](scripts/aggregate.py); the original repository and Index remain the respective product/assessment sources of truth.

| Invocation | Selection and result |
| --- | --- |
| `upstream upgrade` | **One selected original harness, full engineering cycle:** choose one eligible original source once, then stay in that source while investigating distinct functional hypotheses, implementing and natively testing a qualified improvement, and preparing its **fork-local review PR** for the human. Never switch to another original harness during this invocation, even if early hypotheses fail. External publication requires separate approval. |
| `upstream upgrade OWNER/REPO` or `upstream upgrade <contribution-id>` | Same **one-harness, end-to-end** route for a specified original source or verified stable contribution identity. Remain in that original source for the whole run; its first failed hypothesis is not an instruction to choose a different harness. |
| `upstream upgrade VSM derived & informed only S5` (or another explicit `S1`/`S2`/`S3`/`S3*`/`S4`/`S5` scope; optionally with `OWNER/REPO`) | **Function-scoped single-source Upgrade:** screen source-native needs for the requested function before selecting an unspecified original, then lock exactly one harness and pursue only that function's evidence-backed hypotheses through the ordinary full cycle. The VSM-only qualifier retains the existing `ASSESSMENT_DERIVED` / `ASSESSMENT_INFORMED` origin filter. A function label does not grant a new assessment grade or publication rights. [Procedure](#function-scoped-upgrade--evidence-first-selection-and-closure). |
| `upstream upgrade batch N` | **Explicit legacy-compatible breadth mode:** select **N distinct original harnesses** (e.g. 10), not N PRs, fixes, repeated sessions or guaranteed accepted features. For each harness make a source-backed **S1/S2/S3/S3*/S4/S5 disposition** (supported / disproved / not applicable / pending, with an actual reason) to avoid S2-only selection. Deep native tests target the strongest plausible capability rather than mechanically executing six unrelated experiments per harness. If fewer than N eligible sources exist, report the exact shortfall; never pad or duplicate. No new frozen cohort or per-batch issue. |
| `upstream batch [N]` | **Separate technical-screening route**, not an alias for `upgrade`; source-backed repairs may be its main outcome. Use current source and authority. Historical `upstream-old` batch files remain immutable evidence, not automatically current instructions. |


### Function-scoped Upgrade — evidence-first selection and closure

**Optional conversational selection filter, not a new assessment, runtime command, source permission or persistent fork-local enum.** When the operator supplies one or more explicit VSM functions (`S1`, `S2`, `S3`, `S3*`, `S4`, `S5`) with `upstream upgrade`, restrict qualifying hypotheses and their tests to those functions. `upstream upgrade VSM derived & informed only S5` additionally permits **only** the existing canonical `ASSESSMENT_DERIVED` / `ASSESSMENT_INFORMED` origins, with their independent evidence and chronology rules; it is not itself proof of either origin or a positive S5 mapping. For explicitly named `OWNER/REPO`, preselection is skipped but the named source and requested function stay locked. Without a function qualifier, retain the existing unscoped Upgrade procedure. Do not reinterpret `upstream upgrade batch N` or `upstream batch [N]` as one-source function-scoped commands.

1. **Bounded read-only function-first preselection, before source lock.** For an unnamed source, identify plausible real users/agents, blocked outcomes, and public source-native issues, code paths, maintainer requests or reproducible behavior relevant to the requested function. For each candidate screened, pin original identity/default SHA and perform the existing license/contributor-formalities preflight and the separate [autonomy preflight](#autonomy-preflight--before-capability-ranking-and-source-selection) **before** ranking, deep research or source lock; inspect relevant current alternatives and historical canonical Index evidence separately. Prefer a credible material **function-specific user/agent outcome**, testability and lawful effectful path over fork convenience, popularity or a missing Index vector entry. An existing fork/green tests or an `S5 = —` assessment alone is not a selection justification. Record a compact preselection rationale with cited source, need, function hypothesis, nearest existing alternative, test feasibility and uncertainty. This bounded comparison is **not** permission to start a new research batch, create PRs or deeply implement in multiple originals.
2. **Freeze exactly one original, then stay there.** Record `SELECTED_ORIGINAL_REPOSITORY`, original HEAD, `FUNCTION_SCOPE` and origin filter in the human report (report fields only). After binding, continue with distinct hypotheses **inside the same selected harness AND requested function scope**, even if the first hypothesis is disproved, already implemented, or difficult to test. Do not switch to a different original, widen to a different VSM function, relax the VSM-only provenance filter, or turn a repair into a feature to manufacture a PR. If no source has a sufficiently grounded function-specific opportunity, honestly report bounded `EVIDENCE_INSUFFICIENT` or `NO_QUALIFIED_IMPROVEMENT` without falsely binding a harness or promising future work.
3. **Function ownership and return-to-operation receipt.** Before treating a feature as qualified, state the declared system-in-focus and recursion; the function-specific disturbance/decision; the **legitimate decisive decision or feedback right and its actual owner** (human, agent, parent or distributed arrangement); the evidence/inputs reaching that owner; supporting enforcement/transport separately; and the **feedback/closure path into subsequent organizational behavior**. Use current [VSM Profile](https://github.com/opensiro/vsm-harness-profile/blob/main/PROFILE.md) semantics, not ad hoc definitions. For `S1` show operational results; for `S2` regulated interference among operations; for `S3` present system-wide resources/priorities/commitments; for `S3*` an independent complementary audit judgment and corrective return; for `S4` external/future adaptation into present capability; for `S5` legitimate identity/ultimate-policy decisions (including unresolved S3–S4 tension) reaching the proper authority **and returning to govern later operations**. A policy file, prompt, static safety filter, generic human approval, browser permission, router or ordinary security rule alone cannot establish S5 ownership or closure. Do not create artificial six-function components or imply first-party autonomous ownership when the decisive right remains with a human or parent.
4. **Prove a matched outcome rather than an internal check.** Combine this receipt with the existing [overlap/ownership](#existing-work-functional-overlap-and-vsm-ownership-gate) and [material capability-delta](#material-capability-delta-gate-before-implementation) gates. Compare pinned baseline, currently supported workaround and relevant competing PR behavior with the proposed after-state. Predeclare a source-native end-to-end success case observing a **newly possible or materially improved user/agent decision or task** in the requested function, plus a negative unauthorized/absent-owner or missing-feedback case and ordinary-operation compatibility. For S5, test that the correct authority can resolve an identity/ultimate-policy conflict, that an unauthorized actor cannot make that decision, and that its resolution actually changes subsequent behavior; a validator that merely rejects a call does **not** prove a new S5 decision loop. Where the source has no genuine S5-level conflict/decision need, do not add S5 machinery solely to fill a vector gap.
5. **Evidence-based outcome without false closure.** Distinguish a **disproved or nonmaterial function-specific candidate** (`NO_QUALIFIED_IMPROVEMENT` after bounded in-source alternatives), **unverified need/owner/closure/overlap/native result** (`EVIDENCE_INSUFFICIENT`), and a **qualified feature with a concrete non-waivable tool, license, owner or native-test blocker** (`BLOCKED_WITH_HANDOFF`). First try a permitted source-native test setup or other safe alternatives before treating a missing local test runner as an irrecoverable blocker; always report tests actually run, including zero. These labels are **human-report dispositions**, not `.opensiro/` JSON states or a substitute for the existing `MATERIAL_DELTA_SUPPORTED` gate. A lack of the function in an old assessment is never by itself either `MATERIAL_DELTA_SUPPORTED` or a reason to change the canonical Index.

**Illustrative fail-closed cases:** `S5` + only `policy.yaml`/browser permission => **function closure unproven**; an existing PR title or green tests claiming S5 => **overlap unverified** until decision-right and return path are established; a disconfirmed S5 candidate => pursue a different genuinely S5-scoped need **within the selected harness**, not S3/S4 work or a different original. Successful scoped work still obeys one-harness implementation, fork-local review PR consent, five-link disclosure, and separate third-party publication approval. This selection/receipt does **not** change Profile semantics or issue a new autonomy grade.

### Material capability-delta gate before implementation

**Mandatory for a feature claim in any `upstream upgrade`, including assessment-derived/informed-only invocations.** The existing four source-native gates remain necessary but are not sufficient. Do **not** write implementation code, mark `FEATURE_QUALIFIED`, or prepare a publication review PR just because a VSM function is relevant or a deterministic test is easy to pass. Record a concise, source-linked **Capability Delta Receipt** in the working report before the first feature-code mutation, with all of:

1. **Actor and blocked outcome:** name the real user/agent/operator, authentic task/trigger and needed observable output or decision. State what materially cannot be accomplished (or is unacceptably unsafe/costly) through the current supported workflow, not merely which low-level API does not exist.
2. **Source-native baseline and best available alternative:** reproduce/inspect the pinned original behavior, relevant accepted or pending upstream PRs, existing feature flags and plausible user workarounds. A different API signature, narrower health check, convenience wrapper, additional diagnostic or cosmetic configuration option alone does not establish a material capability delta.
3. **After-state and measurable counterfactual:** state the task newly possible or demonstrably improved, the S1-S5 mechanism, and a matched native scenario that observes an end-to-end **user/agent result**, not just an internal call. Define the success criterion before coding (e.g. two competing agents each complete their assigned operations without cross-agent interference versus the original failing); include a negative/compatibility check.
4. **Materiality and honest scope:** explain why the observable difference matters to the source users and cannot be met comparably by the existing workaround. State any critical guarantee the proposal **does not** supply. If the real user problem needs ownership enforcement, showing only a target-existence probe does not qualify as solving isolation. No universal invented benefit score or numeric threshold is required.
5. **Disposition and evidence:** explicitly choose `MATERIAL_DELTA_SUPPORTED`, `DELTA_PENDING` or `NO_MATERIAL_DELTA` in the **human report only** (not new persistent JSON enums), cite pinned source / native proof, and distinguish fact from a hypothesis. `MATERIAL_DELTA_SUPPORTED` permits consideration of implementation only when the existing need/mechanism/counterfactual/scope, permissions and native validation gates also pass; it never implies accepted PR, VSM grade change or deployed benefit.

**Fail closed before coding:** `DELTA_PENDING` or `NO_MATERIAL_DELTA` blocks Upgrade feature implementation and fork-local review PR handoff. Continue bounded research into **other materially distinct hypotheses inside the same selected harness**, not another original source. Legitimate reliability repairs can be handled honestly through the separate `upstream batch` route; they are not silently promoted to Upgrade feature results. If a speculative implementation already exists when this gate is applied, keep it labeled **unqualified**, record the failed/missing evidence, and do not submit it as an Upgrade PR merely because all unit tests passed. Rework or discard it only through independently authorized edits, without erasing historical receipts.

### Existing-work functional overlap and VSM-ownership gate

**An existing issue, upstream PR, green native test suite or matching VSM vocabulary is evidence of a proposal, not proof that a user capability or VSM function is already covered.** Before rejecting a hypothesis as duplicate, declaring `NO_QUALIFIED_IMPROVEMENT`, or choosing a new implementation, complete a bounded, source-linked **Overlap and Ownership Receipt** in the current working report:

1. **Assessment-to-source mapping:** pin the current normative [VSM Profile](https://github.com/opensiro/vsm-harness-profile/blob/main/PROFILE.md) function semantics, the canonical Index assessment's actual `reviewed_at`, `review_ref` and immutable assessment SHA, then separately inspect the selected original harness's current default HEAD. An older `S3 = —` or `S4 = —` is a historical baseline, **not** a current verdict or a prediction of any PR's behavior. Assess the *specified function and declared system boundary*; do not call S2 coordination, a static resource cap, helper memory or a health probe S3/S4 merely because related code exists.
2. **Decision owner and closure:** name the actor that actually chooses/revises the organizational decision, its right and system-wide view, the enforcement mechanism, input feedback and observed closure. For S3 distinguish cross-unit resource/priority/commitment regulation from per-target routing, static quota enforcement or recovery. For S4 distinguish external/future modeling, adaptation options and two-way return to present S3 capability from current-task retries, diagnostics or mere skill accumulation. For S1/S2/S3* apply the corresponding Profile-defined operational, coordination and independent-audit ownership/closure tests. For S5 distinguish a legitimate identity/ultimate-policy decision and its return to later operations from a static policy file, routine approval, prompt, safety check or ordinary permission enforcement; a human/parent decision owner is valid when its actual decision and closure are observed. If any decisive link is absent or externally owned without a proven return path, report **function coverage unproven**; do not infer autonomy, a grade change or that missing code alone constitutes a user feature.
3. **Current native behavior versus competing work:** inspect the first-party source and each relevant open/merged/closed PR's **actual current head/diff, declared boundary, test evidence, maintainer decisions and compatibility**. Where executable and permitted, compare matched native baseline/PR-head scenarios with positive, negative and cross-agent cases. Passing tests prove only the cases executed, not full functional coverage, deployment or acceptance. Capture a compact `baseline → competing PR → remaining gap` matrix with exact source refs, distinguishing *implemented on main*, *proposed but unmerged*, *partially covered*, *unverified* and *genuine duplicate*.
4. **Prefer continuation or integration before novelty:** for a verified useful residual capability, first evaluate updating **OpenSiro's own existing compatible contribution**, proposing a bounded follow-up/dependent branch against the same selected original, or coordinating with the existing PR's owner **only with the required exact public-communication consent**. Never mutate another author's branch without actual write rights or assume that adding code to a third-party PR is authorized. Explicitly explain why reuse, extension, separation or no new patch is the least-overlapping source-native route.
5. **Evidence-based disposition:** use **`OVERLAP_CONFIRMED`**, **`PARTIAL_OVERLAP`** or **`OVERLAP_UNVERIFIED`** as *report-only descriptions*, not new persistent JSON enums. A PR title/summary, historical assessment label or tests alone cannot justify `OVERLAP_CONFIRMED`. If one hypothesis overlaps, investigate materially distinct hypotheses **within the same selected harness and any explicitly requested function scope** before a terminal outcome. `EVIDENCE_INSUFFICIENT` is preferred over `NO_QUALIFIED_IMPROVEMENT` when material gaps, authority, alternative behavior or native capability remain unverified.

This receipt **does not bypass** the separate material capability-delta gate: evidence that a VSM function is absent does not automatically prove a useful feature, and an existing PR missing S3/S4 closure is not an automatic instruction to implement a new metasystem. Do not edit the canonical Index assessment or claim re-assessment from PR tests; any formal re-assessment follows the Index/Skills owning procedure. Keep the selected original harness fixed and preserve third-party publication consent.

**VSM-only operator filter:** the conversational qualifier `upstream upgrade VSM derived & informed only` narrows admissible improvement origins to the existing canonical `ASSESSMENT_DERIVED` and `ASSESSMENT_INFORMED` types. This is a *selection filter*, not a new classification or proof of usefulness: a source-first general repair with a context-only Index link is not automatically `ASSESSMENT_INFORMED` without an actual documented VSM mechanism affecting the proposed feature. An unsupported causal prediction must not be upgraded to `ASSESSMENT_DERIVED`. The material-delta gate applies equally to both permitted types.

### End-to-end single-source Upgrade — finish at human PR approval

**Scope invariant: exactly ONE original harness per `upstream upgrade` invocation.** When no `OWNER/REPO` is given, perform bounded read-only preselection, license/formalities and autonomy checks to **select one original source**. After selection record its immutable source identity and lock the remainder of this invocation to that source, its correctly parented `opensiro-contributions` fork and its distinct improvement hypotheses. **Do not switch to a different original harness** on a failed first attempt, an already-implemented candidate, a missing `opensiro/meta` branch, an unavailable native runner or a candidate-specific human gate. A new original source requires an explicit separate user instruction, not an internal fallback. `upstream research batch N` may be proposed as a *future* dedicated multi-source research name, but it is **not** an active rename or permission to turn `upgrade` into a batch.

**The target is still the entire engineering cycle, not discovery or research.** A successful result is `READY_FOR_HUMAN_PR_APPROVAL — NOT PUBLISHED`: a concrete source-native feature has passed need / mechanism / counterfactual / scope, code and tests are on the authorized target fork product branch, and the full original-template PR proposal is prepared for human review using the **fork-local review PR route** described below. No third-party PR/draft/comment or public fork-local proposal is automatically published. This is an on-demand conversational execution contract, not a background executor, new `.opensiro/` enum, unlimited research promise or PR quota. `upstream upgrade batch N` remains a separate explicit chat-scoped research compatibility route.

1. **Choose and bind one harness before prolonged implementation research.** Verify original `OWNER/REPO`, its source/default SHA, real license, contributor requirements, existing PRs/feature duplicates, matching working fork and any **existing** `opensiro/meta` owner-control; a confirmed missing branch is [provisioned after actual fork-write authorization](#upgrade-metadata-materialization--missing-opensirometa), and an unreadable ref is not presumed missing. For an unspecified target, consider other sources **only before final source selection**; when a function is specified, first apply [function-scoped read-only preselection](#function-scoped-upgrade--evidence-first-selection-and-closure), then complete license/formalities and autonomy preflights before using contributor popularity among comparably feasible, function-credible candidates. Favor source-native need/testability and a realistic effectful-rights path. Record `SELECTED_ORIGINAL_REPOSITORY` as a report field (not a new JSON enum). Once bound, no further cross-harness candidate search occurs in that run. `Stay inside the named original source` also applies when the user supplied `OWNER/REPO`.
2. **Continue within the selected harness without intermediate continuation prompts.** Investigate plausible distinct NEW user/operator capabilities in that same original, checking all relevant VSM function ownership/control hypotheses as appropriate, existing workflow alternatives, source-native baseline and counterfactual, negative/compatibility controls and four admission gates. Apply the [material capability-delta gate](#material-capability-delta-gate-before-implementation) **before feature coding**. When a hypothesis is falsified, duplicate, merely `REPAIR_ONLY` or unsuitable, record the result and try a **different hypothesis in the same harness and any explicitly requested function scope** if one is evidence-backed. Do not force six feature patches or a meaningless change. Progress reports are not requests to type `continue`.
3. **One-harness blockers and terminal evidence.** A candidate-local `CLA/DCO`, maintainer pre-approval, long-term maintenance undertaking, **unavailable or unauthorized meta provisioning**, `PAUSE/STOP`, `DORMANT` or missing source-native test capability is not silently waived. It may block effectful work **in the chosen harness**; continue permitted read-only evaluation of other opportunities inside that same source where useful. If no safe qualified improvement remains, report `BLOCKED_WITH_HANDOFF`, `NO_QUALIFIED_IMPROVEMENT` or `EVIDENCE_INSUFFICIENT` with exact source SHA, checked hypotheses, native tests actually run (including 0), fork branch/head if present, remaining options and the decisive decision/tool/rights owner. **No cross-harness fallback is permitted to avoid this honest stop.** These are report statuses, not new fork-local JSON states.
4. **Effectful authority is independent of choosing a source.** `SCREENABLE_READ_ONLY` is not permission to fork, implement derivatives, alter `.opensiro/`, sign CLA, bypass a maintainer's required issue-first decision or resume a paused project. Before every effectful step verify the original license and contributor policy, verified fork parent, product branch/base/head, one-writer meta controls, permissions, overlap, native runner and source drift. `DORMANT/PAUSE/STOP` requires an actual permitted decision/RESUME, not `upstream upgrade` as implicit consent.
5. **Implement and validate, not merely propose.** After the four admission gates and effectful permissions pass, **ensure the fork's `opensiro/meta` and one stable improvement record exist**, creating/validating them through the [on-demand metadata procedure](#upgrade-metadata-materialization--missing-opensirometa) if confirmed missing. Then implement a scoped user-visible feature in the selected matching `opensiro-contributions/<fork>` **product branch**. Independently validate source-pinned before/after behavior, positive, negative and compatibility cases, applicable native test/build/CI commands, exact diff, fork head SHA and original source drift. Put OpenSiro-only `.opensiro/` evidence/events on **`opensiro/meta` only**, never in that product PR. Read back the exact metadata commit and verify the contribution in `scripts/aggregate.py`; lack of an authorized writable ref is a genuine **source-local** blocker, not an excuse to switch harnesses. Do not claim `READY` if tests or code do not actually exist.
6. **Human review through the working fork, not a text-only handoff.** The exact proposed *external* PR title/body must be reviewable as **one fork-local PR from the verified product branch to that same `opensiro-contributions/<fork>` fork's source-matched default branch**. Keep its title/body source-template-compliant and include the [current AI-assisted disclosure](docs/UPGRADE_PR_REVIEW.md), date/source references and honest human-publication status. This fork PR is a **proposal/review record**, not a request to merge into fork `main`; never merge it as a side effect of approval. Because a **public fork-local PR itself is a public communication**, first display the exact proposed fork-local destination, title, body, branch/SHA and diff and obtain the independently required current-conversation consent **before creating/updating that PR**. If consent is not yet given, show a precise read-only compare URL/branch/diff and complete PR draft, mark `AWAITING_FORK_LOCAL_PR_APPROVAL`, and do not claim the review PR already exists. Reuse one existing fork-local PR for the same improvement when valid; never create a duplicate PR solely for appearance.
7. **Show the fork-local PR link and stop for the human decision.** After authorized fork-local PR creation, verify it through first-party readback and give the human its **actual `opensiro-contributions` PR URL**, source target `OWNER/REPO`, current fork/product head SHA, original-template prospective external title/body, native test receipts, origin/evidence and legal limitations. The end condition `READY_FOR_HUMAN_PR_APPROVAL — NOT PUBLISHED` requires a verified fork-local `.opensiro/` record at a pinned `opensiro/meta` SHA, independently tested product work, and an appropriately authorized fork-local review handoff; it means **external target PR NOT published by this Upgrade** and the human may approve its exact outward action later. When source code is fully validated but a public fork-local PR cannot be opened due to its separate consent gate, report preparation ready **but review PR pending**, not a fabricated URL or completed approval step. A final external PR (including Draft) or an edit to a previously public external PR still needs **exact current-conversation consent** and fresh current-conversation owner approval of the exact original destination/action, final title/body and verified diff; material changes require renewed approval.

**Mandatory `opensiro-contributions` links for PR handoff and body.** The human review packet **and the prospective external PR's AI-assisted disclosure** must include verifiable GitHub links to the matching `opensiro-contributions/<fork>` (working fork), its exact product branch, **40-character implementation commit**, actual fork-local review PR, and pinned `.opensiro/contributions/<stable-id>.json` under `opensiro/meta`. Require all links to name the same independently verified fork and pin the exact proposed diff/assessment provenance. A PR description with only a generic `## AI assistance` paragraph, no Index date/review SHA when a verified assessment exists, or missing fork/review/commit links **fails the new-publication preflight** even if the technical tests passed. If fork review is not yet authorized/created, report `NOT_CREATED — awaiting exact fork-local PR consent` and **do not invent a URL or claim `READY`**; if the PR was *already* published historically without an internal review PR, identify this truthfully as `NOT_CREATED — historical PR; no prior fork-local review PR`, not retroactive authorization. Keep [the normative disclosure form and structural validator](docs/UPGRADE_PR_REVIEW.md) current with this rule. No external PR edits without separately approved exact public text.

### Resumable Upgrade link and context checkpoint (mandatory)

**Do not reconstruct a pending PR from chat memory.** At every resumed Upgrade, human approval, or proposed public GitHub action, first re-read the verified fork's latest independent opensiro/meta state and exact stable contribution record, then the original source issue/PR, fork parent and current product/default SHA, live existing fork-local PR status, original PR status and native test evidence. Check the record's canonical **schema v2** and origin classification, current PAUSE/STOP controls, and whether a later owner STOP has suspended publication. The record remains the sole durable source for intervention scope, owner decision and next action; do not copy a second mutable activity ledger into Upstream. Any prior-chat approval cannot substitute for exact current-action approval, and a later STOP cancels pending publication even after a prior approval. Do not turn a STOP limited to outward communication into an unrequested blanket engineering STOP.

Generate a full **five-link handoff packet** from independently verified fork/meta/code refs and the canonical contribution using the source-only [resume handoff helper](scripts/upgrade_handoff.py). It prints the verified working fork, product branch, exact 40-character commit, actual fork-local review PR or an explicit NOT_CREATED marker, and pinned metadata contribution; also pin the source request/assessment and state current test gaps/next action. The helper verifies local record/schema/same-fork consistency, **not** GitHub availability, license or consent. **Do not ask for or act on PR publication approval until the actual proposed full body passes the helper's --body-file exact-ref/origin preflight and** [scripts/validate_upgrade_pr_links.py](scripts/validate_upgrade_pr_links.py) in preview mode and its links match independently re-read first-party GitHub refs. Repeat the validator in new mode and live PR readback before any new external PR. A failed/missing checker, stale head/meta, missing provenance URL, invented review PR, unsupported capability delta, or active owner publication hold is PR_BLOCKED_NO_WRITE. Keep the current attempt within the same original harness.

**Session boundary:** finish the permitted stages now, never promise asynchronous continuation. A genuine restriction or an exhausted set of hypotheses **inside the selected source** can end the invocation without a PR; state exactly what is and is not completed. The safe stop is not permission to silently select another harness.

### Upgrade metadata materialization — missing `opensiro/meta`

**Mandatory for full-cycle `upstream upgrade` and `upstream upgrade OWNER/REPO` when an independently qualified intervention is being implemented or handed off.** A missing `opensiro/meta` is a **recoverable initialization task**, not evidence that there is no improvement and not an automatic reason to abandon the current candidate. A `batch N` or read-only screening report **does not** create branches or issue/PR records. This is an agent procedure using existing authorized GitHub capabilities, **not** a new always-on runner or authority grant.

1. **Discover, then independently authorize.** Re-read the original source SHA, actual `opensiro-contributions/REPO` fork (`fork=true`, `parent.full_name` matches original), current fork default/product heads, first-party PR facts, root license and contributor-formalities evidence. Check any available previous fork `.opensiro/` / human control decision, existing contribution IDs, branch collisions and exact fork write permissions. Distinguish a **verified 404 for the branch** from 403/429/API failures or a malformed/partially initialized branch; the latter are `UNKNOWN` / blocked, never grounds for a new branch. **`PAUSE`, `STOP`, `DORMANT`, owner-only grants, source rights and third-party publication consent remain independent gates.** Missing metadata means missing evidence of `ALLOW` — never infer it. Do not mutate the fork without the actual current authority for **that** effectful action.
2. **Initialize safely if absent and authorized.** Recheck that the metadata ref is still absent immediately before creation. Create `refs/heads/opensiro/meta` from a **pinned current fork default-branch commit** (not from the work/PR branch), without force-push, default-branch edits, product-source merges or changes to original-project code. On the new metadata branch alone, commit valid v1 `.opensiro/state.json` and `.opensiro/contributions/<stable-id>.json` for this concrete improvement, plus an attributable significant event when there is a real recordable decision or checkpoint. `state.json` names the exact original and verified fork; **new `contributions` are schema v2 and MUST include validated `contribution_type` with evidence/rationale before the metadata write**; `contributions` links real pinned source/working branches, observed native evidence, next action and **verified existing** external PR URLs. `last_event_id` may be `null` if no attributable event exists. Never invent native tests, prior approvals, `ALLOW`, source PRs, maintainer consent or retrospective event timestamps. Use `PAUSE` / `DORMANT` for a bootstrap without an independently evidenced active owner authorization; an explicit, attributable owner authorization is required for `ALLOW` / `ACTIVE`. Provisioning a PAUSE record is **not** an implicit `RESUME`.
3. **If `opensiro/meta` exists, resume rather than overwrite.** Validate its `state.json`, `original_repository`, `working_fork` and owner control first; reuse an existing matching contribution ID (including old source/replacement PR chains), or add a **new stable ID only for a genuinely distinct intervention**. Never reset a PAUSE/STOP, overwrite events, discard historical evidence or move `.opensiro/` onto a product branch. Commit with an observed metadata HEAD and optimistic compare-and-swap/single-writer coordination. If a competing writer creates the branch or advances its HEAD, stop and re-read/reconcile rather than force updating or making duplicate IDs.
4. **Read back and require coverage.** After provisioning/updating, fetch the exact committed `opensiro/meta` HEAD and read `.opensiro/state.json` and the intended contribution file at that SHA. Confirm original/fork identity, stable ID, source revision, relevant product branch and real PR links; then invoke the [read-only aggregator](scripts/aggregate.py) on **that fork** to verify that its contribution can be projected (and live external PR status if the PR is already published). An aggregator read error or missing metadata is `COVERAGE_UNKNOWN`, **not** zero contributions or a successfully synchronized portfolio. Record exact meta SHA and report the limitation; `READY_FOR_HUMAN_PR_APPROVAL` is unavailable until the fork metadata verification and other native/rights gates actually pass.
5. **Backfill an already published PR without creating another.** For a verified pre-existing original PR, reconcile its first-party URL, head/source SHAs and genuine lifecycle state into **one** matching contribution. Create the missing metadata branch only under the same fork-write authority. Do not modify the already published external PR, inflate independent improvement counts, invent a fresh `READY_FOR_HUMAN_PR_APPROVAL — NOT PUBLISHED` state or mark PR acceptance; report the external PR's separately observed state.

**Fail-closed handoff:** if the verified fork is unavailable, its metadata branch is unreadable/colliding, identity or licensing fails, existing `PAUSE/STOP` forbids writes or effective authority is missing, report `META_PROVISIONING_BLOCKED` with the exact fork/source/ref, observed 404 vs error, permission owner and next safe action. This is a **candidate-local** blocker; continue only permitted read-only or independently qualified opportunities **inside the same selected original harness**. **Never switch to another original source** to escape the blocker; the [one-harness rule](#end-to-end-single-source-upgrade--finish-at-human-pr-approval) remains binding. The existing **external-publication approval gate** still applies before any outward public comment, fork-local proposal/PR or third-party PR.

### License and formalities first — human gate category

**Order is mandatory for new source selection:** (0) discover original candidate identities without assuming eligibility; (1) **read-only license and contributor-formalities preflight**; (2) separate a screenable research pool from human-decision/unknown cases; (3) only then prioritize the screenable pool by contributor popularity. An explicitly named source still goes through step (1). Popularity, existing forks, a Github license badge and prior external PRs are not substitutes for rights.

Use the existing read-only [`upstream-old` intake preflight](https://github.com/opensiro/upstream-old/blob/main/docs/CANDIDATE_INTAKE_PREFLIGHT.md) and [implementation](https://github.com/opensiro/upstream-old/blob/main/scripts/candidate_intake_preflight.py), or equivalent **first-party source-pinned readback** when its host is unavailable. Check actual root license text and scope (not only SPDX metadata), repository identity and default/source SHA, `CONTRIBUTING`/contributor instructions, CLA/DCO/sign-off, issue/PR-before-implementation policy, required authorization, source availability and independently observed restrictions. Note linked or non-root licenses, generated/vendored code, copyright uncertainty and whether an existing issue/PR already handles the same request. This stage is **evidence collection**, not automated legal clearance: historical preflight status `LICENSE_REVIEW_REQUIRED` proves license text was observed, **not** `LICENSE_ELIGIBLE` or permission to write. A missing root license yields `LICENSE_BLOCKED` or a bounded alternative-license investigation, **not** a claim that the project is unlicensed in every location.

**Three distinct selection dispositions (narrative, not a new fork JSON enum):**
- `SCREENABLE_READ_ONLY`: original identity and license/policy evidence is readable, and no decisive known obstacle to further **non-derivative, read-only** research has been found. This does **not** mean `LICENSE_ELIGIBLE`, CLA/DCO acceptance, permission to fork/modify/publish or a passed implementation gate; confirm actual rights again before each effectful stage.
- `HUMAN_GATE_PENDING`: relevant license grant/compatibility is ambiguous or restrictive, human-person CLA/DCO, contributor assignment, private/security access, repo/fork/runner availability or another authorization decision is needed. **Do not discard the source, assume availability, contact maintainers, create a fork or implement a derivative** to resolve this automatically. Record the precise evidence/question and defer the *availability/access decision* to the human.
- `INSUFFICIENT_EVIDENCE`: network/API failure, inconclusive/missing evidence, ambiguous source identity or incomplete policy reads. Never silently transform this into eligibility, a legal rejection or zero contributions. Record an exact retry or responsible human decision.

**Separate GitHub Issue category for genuine human requests:** use [`Human gate — license, formalities & availability`](https://github.com/opensiro/upstream/issues/new?template=human-gate.yml) in this internal `opensiro/upstream` repository. Create **only when a concrete, non-duplicated human decision actually needs tracking**, not per batch or per routine license check. Before opening, search existing human-gate issues and any linked fork-local state; append a linked request to the same existing issue if it has the **same decision owner and exact scope**, otherwise create one issue for the genuinely independent decision. Use source, pinned evidence URLs/SHA, decision needed, gate type, current safe stage and next owner. Do not copy secrets, private policy text or third-party code. An issue is a **human-decision inbox pointer**, not another canonical contribution ledger, a blanket work permission, an autonomous approval request to a third party or a silent `PAUSE` override. Chat-only batch outcomes remain chat-only; no issue is created just to report a blocked row. The owner may explicitly triage and decide availability/access later without freezing all other independently screenable work.

In reports show the counts **screened / read-only screenable / human pending / insufficient evidence** separately from popularity rank, functional opportunities and PRs. A human-gate issue can say what is unknown; closing it or observing a license badge does **not** imply CLA, legal clearance, an externally approved PR or an authorized executor. Keep exact third-party-publication consent and fork `PAUSE/STOP` independent.

### Autonomy preflight — before capability ranking and source selection

**Mandatory for every newly considered original source, including an explicitly named target:** after the existing [license/formalities screen](#license-and-formalities-first--human-gate-category), run a bounded **read-only contributor-path feasibility check** **before** popularity ordering, prolonged VSM/native capability qualification or binding the original harness. A bounded first-pass search for function-specific user needs may identify the candidate pool, but it does not waive this preflight. Reuse the license/CLA/DCO evidence already collected; this is a separate check of whether OpenSiro can actually complete an agent-assisted contribution through the original project's permitted workflow, **not** a new legal clearance, autonomy grade, source-selection veto or permission to publish.

Record source-linked, dated evidence for each of these distinct questions:

1. **Permitted license and derivative path:** inspect the real license text/scope and relevant third-party conditions through the existing legal preflight. A permissive SPDX badge or an existing OpenSiro fork alone does not establish rights to implement or submit.
2. **Who may contribute and how:** can a non-core contributor propose their own external PR, or is the route **issue/plan only**, maintainer-owned implementation, an assigned issue, a specific ready-for-work label, pre-approved design, Discord discussion or CLA/DCO step? Read the current `CONTRIBUTING`, PR/issue templates, applicable `AGENTS.md` and maintainer policy; distinguish requirements **before coding**, **before PR** and **before merge**.
3. **AI use and personal attestations:** distinguish AI-assisted implementation/disclosure that is permitted from an AI-authored PR or public message the project restricts. Identify any mandatory human-authored PR field, human review certification, personal agreement/signature, DCO sign-off or identity assertion. **An agent must not invent a human review, fill human-only fields, sign a CLA/DCO as a person or self-approve a maintainer decision**; unresolved personal acts require the actual authorized human.
4. **Runnable native validation and publishable path:** identify source-native build/test commands and realistic executor access, required PR form and CI/review gates. Missing runner, unknown bot policy, uncertain fork/write rights or unverified instructions remain **unknown**, not a passed autonomy check; distinguish review workload from an outright prohibition on external PRs.

**Selection and reporting:** alongside the existing `SCREENABLE_READ_ONLY` / `HUMAN_GATE_PENDING` / `INSUFFICIENT_EVIDENCE` screening disposition, state in plain language whether the source has a verified non-core PR route, a route conditional on a genuine human/maintainer step, an issue-only route, or an unverified route. Cite the decisive policy/issue/PR URLs, original revision or observation time, exact unsatisfied gate, responsible decision owner, and the **next permitted stage**; absence of a discovered CLA or AI restriction is **not** proof none exists. These are report descriptions, **not** additional persistent fork JSON states or automatic issues.

For **autonomy-first source selection**, among sources with a credible original-native user need and any explicitly requested VSM function scope, prefer a proven, AI-compatible non-core PR path without unresolved personal attestations or maintainer prerequisites, with runnable native tests, **before** comparing detailed functional upside or contributor popularity. Among comparably feasible sources, preserve the existing contributor-popularity priority; do not invent a numerical autonomy score or discard a legitimate human-gated source from read-only research. If the operator explicitly names a source, the preflight reports its restrictions **without selecting a replacement**. After any source is bound, a failed gate is a **same-source** blocker/handoff, never permission to switch harnesses. This screening does not override the separate fork-local owner control, effectful write authorization or exact current-conversation consent for any public fork-local or third-party action.

### Default popularity priority — no contribution quota

For an unconstrained `upstream upgrade` selection, run the [license/formalities screen](#license-and-formalities-first--human-gate-category) and [autonomy preflight](#autonomy-preflight--before-capability-ranking-and-source-selection) **before** popularity ranking. Among comparably feasible original sources with a credible source-native need, **popular original repositories first**: rank distinct original projects by their **number of unique GitHub contributors** (not the number of OpenSiro PRs, commits or batch appearances). Use current first-party public contributor data and an observation timestamp. If contributor count is unavailable or unreliable, use source-repository stars as a *labeled fallback*, not a fabricated contributor count; ties use known current maintainer demand and source freshness. Never infer usefulness, license clearance or permission from popularity alone. A user-named source overrides the default popularity order, **not** the initial license/formalities screen, rights or human access decisions.

**Distribution of OpenSiro work** (independent contribution IDs, not PR counts): use one **breadth-first** research opportunity per distinct eligible project before repeatedly allocating attention to the same source. Within that pass, start with the most popular. After broad coverage, use a **gentle linear priority** for additional opportunities: rank-percentile weight grows from **1× to 2×** from least to most popular among the eligible pool. This is *selection preference*, not a minimum/maximum PR count, guaranteed implementation, artificial patch, or objective success metric. If the operator specifies `uniform`, keep one-source-one-turn round-robin instead. A qualified source need and independent native evidence always outrank a popularity weight; skip duplicated, infeasible or already solved ideas. Report the observed number of **OpenSiro independent contribution IDs per source** separately from popularity. Do not manufacture contribution counts to match a curve.

### Chat-native batches, no per-batch GitHub artifacts

`upstream upgrade batch N` and `upstream batch N` are **bounded chat-level research/reporting sessions**. Their normal result is a compact table **in the current chat**, not an issue, PR, frozen cohort JSON, batch-specific branch, GitHub Action, permanent reservation, control-plane object or obligatory fork metadata event. Use no extra artifact if conversation output is sufficient. Existing `.opensiro/` records, original issues/PRs, source revisions and historical `upstream-old` receipts remain the durable references where they already exist. A newly verified substantive, authorized intervention may update its **single fork-local contribution** under the ordinary gates; batch screening itself does not write.

The chat report must show for each selected original source: source link/revision; license/formalities evidence and screen disposition (`SCREENABLE_READ_ONLY`, `HUMAN_GATE_PENDING`, or `INSUFFICIENT_EVIDENCE`), and the separate evidence-backed autonomy/PR-path feasibility with any unmet human or maintainer gate, with a human-gate issue link only where an actual request exists; observed popularity measure and its timestamp or `UNKNOWN`; existing independent OpenSiro contribution count if known; S1/S2/S3/S3*/S4/S5 disposition; proposed *new* task/output and nearest existing alternative; feature vs repair vs unsupported result; actual native evidence or `NOT_TESTED`; GitHub PR observations as separately labeled facts; smallest next action/permission blocker. The closing line states distinct sources requested/checked, grounded opportunities, actual native tests, accepted changes if independently read back, and unknown coverage. A batch ending with no new capabilities is an honest result, not a reason to issue a new PR.

A **chat-only hypothesis cannot alone prove immutable pre-source Index-first chronology**. For a strict `ASSESSMENT_DERIVED` claim, use an already verified prior pinned/datable Index-first prediction (and source/evidence receipts); absent that, report `ASSESSMENT_INFORMED` / `GENERAL_UPSTREAM` / `INSUFFICIENT` as justified rather than creating a gratuitous GitHub issue/PR to manufacture provenance. Never treat a chat report as separately independently executed native test evidence.

### Upgrade decision sequence — one improvement, not one PR

1. **Read and select, without writing:** establish today's Organization selection and active operator instruction; inspect the [Upstream aggregate](scripts/aggregate.py) with explicit coverage warnings, exact original GitHub issue/PR statuses, old evidence and deduplicated `.opensiro/` IDs. `DELIVERED`, `MERGED`, `CLOSED_UNMERGED` and `BLOCKED` are separate facts; an old merged fix is not a new capability to re-propose. Missing metadata is `UNKNOWN`, not evidence of no opportunities. Prefer credible unmet operator/maintainer demand, source-native reachability and testability over filling a quota or chasing low assessment grades.
2. **Name the new task before prolonged code exploration:** give a concrete **actor → trigger → new action/decision → observable output/API**, the closest existing original-version workflow or alternative, and a bounded benefit proxy (task possible, correct evidence discrimination, reduced decision latency/cost, etc.). A missing API, low VSM grade, failure-injection mock or empty slot in a six-function table is not proof of need. A pure bug fix, retry/locking regression, dependency upgrade or refactor is `REPAIR_ONLY` unless an independently evidenced new user task is delivered. Valid repairs remain useful but report them separately from upgrade's feature findings.
3. **Link the VSM hypothesis without causal laundering:** use the relevant S1/S2/S3/S3*/S4/S5 mechanism(s), decisive runtime owner, feedback/control boundary and original source evidence. Consider all plausible functions, not S2 by default; do **not** require six product hypotheses or grade changes. `ASSESSMENT_DERIVED` requires a **pre-existing dated, pinned Index-first specific prediction** before fresh original-source study. For issue/source-first needs use `ASSESSMENT_INFORMED` or `GENERAL_UPSTREAM`; mark insufficient chronology as `INSUFFICIENT`. Never re-label a historical source-first result as Index-derived after the fact.
4. **Qualify or falsify one bounded opportunity:** pin original code/issue and current supported workflow, establish the native baseline and smallest counterfactual, and predeclare the proposed new output under matched fixtures with a negative/compatibility control. Before implementation, independently record `MATERIAL_DELTA_SUPPORTED` with source-linked evidence for a material new end-to-end task, or fail closed as `DELTA_PENDING` / `NO_MATERIAL_DELTA` under the [material capability-delta gate](#material-capability-delta-gate-before-implementation). After authorized implementation, test the actual new outcome against the predeclared counterfactual. Resolve source-native **need / mechanism / counterfactual / scope** as explicit `PASS` or `PENDING` with evidence. A passing test of existing behavior alone, a mocked impossible exception, a signature-only test, or passing CI without the new user output does not establish benefit. If a real agent/model outcome cannot be tested in the permitted environment, state that limit; do not claim task-quality gains from script tests.
5. **Only after admission, check effectful authority:** original license, CLA/DCO, contributor policy, exact fork parent, current branch HEAD, `owner_control`, attention state, work collision and explicit grant. **`PAUSE` or `STOP` blocks new effectful steps; `DORMANT` is not automatic consent to resume engineering.** A request to review or run `upstream upgrade` is not itself a fork-local owner `RESUME`. Read-only investigation and an exact proposed next decision may continue; do not mutate metadata or product branches while blocked.
6. **Implement only a demonstrated need:** under independently verified fork-write authority, first ensure `opensiro/meta` and the stable improvement record exist, creating them [on demand](#upgrade-metadata-materialization--missing-opensirometa) if confirmed missing. Prepare source-native code/tests on an allowed fork product branch and independent before/after verification; keep OpenSiro-only records/events **only** on `opensiro/meta`, reusing the contribution ID for original/replacement PRs. Do not add an Upstream issue, PR, permanent process, manifest or fork merely for recordkeeping.
7. **Finish at verified fork-local review or a genuine single-source blocker:** single-source `upstream upgrade` follows the [one-harness end-to-end route](#end-to-end-single-source-upgrade--finish-at-human-pr-approval) through implementation, native tests, and the proposed external title/body **on an authorized review PR in the matching `opensiro-contributions` fork**. A public fork-local PR and a later third-party PR each require their own exact applicable consent; do not open either without it. Do not switch to a different harness to escape a failed hypothesis, CLA or PAUSE. Original GitHub PR state is independent of utility; no forced patch/PR quota.

**Operator output per source:** original URL + source SHA; existing fork/meta SHA or `UNMAPPED`; existing contribution IDs and external PR readback; actor/task/output, baseline/alternative, VSM mechanism and origin classification; bounded benefit proxy and decisive native result; four admission gates; `FEATURE_QUALIFIED`, `OPPORTUNITY_PENDING`, `REPAIR_ONLY`, `CLOSED_NO_CHANGE` or `BLOCKED` **as narrative dispositions, not invented JSON work states**; smallest next action and its decision owner. For `batch N`, report **N distinct selected sources (or explicit shortfall)**, six per-source function dispositions, feature vs repair counts, and independently verified contributions/PRs separately. Report `SCREENING_COMPLETE` separately from `OPPORTUNITY_DECIDED`; never declare all six product capabilities researched merely because six checkboxes exist.

## Implement and validate

Inspect original source, actual fork `parent.full_name`, default branch, license/CLA/DCO, branch SHA, contributor rights and overlapping PRs before source changes. A verified missing `opensiro/meta` is provisioned only **after** its independent effectful authority gate, from pinned fork default HEAD and without touching product branches. The fork has **separate work branches for product code and `opensiro/meta` for OpenSiro-only evidence and events**; never include `.opensiro/` in the original project's PR diff. Don't edit upstream README or CI for OpenSiro metadata. The metadata branch itself must be protected against lost updates through optimistic HEAD checks and one-writer-per-fork coordination.

Demonstrate feature behavior in the original native stack with source-pinned baseline/after evidence and appropriate negative/compatibility control; for a repair, reproduce a real reachable original failure. Record exact fork/source SHA, test commands, result and limitations as links; large raw logs stay in their original technical owner, never copied to Upstream. If a fork cannot be verified, preserve a minimal blocker at intake; do not pretend a branch or passing CI exists.

## Deliver, observe, choose attention

Use the original PR template, policy and AI disclosure. Before outreach follow [External-publication consent](#external-publication-consent). A specific original/replacement PR chain maps to the **same contribution ID**. Source-owned external status is one of `OPEN`, `MERGED`, `CLOSED_UNMERGED`, `UNKNOWN`, with separate draft/review/CI qualifiers. Never interpret closed-unmerged as disproved usefulness or merged as measured deployed benefit.

Maintain the independent fork **attention** setting `ACTIVE`, `WATCHING`, `DORMANT`, `ARCHIVED`. These are elective, reversible choices about whether to perform engineering or scheduled observation; not a maintenance commitment or TTL. State/decision changes and human `PAUSE`, `STOP`, `RESUME` are attributed **significant** events in the fork metadata. A cooperating executor must re-read owner control and effective authority before every new effectful step. Writing STOP does not cancel already-running processes.

At meaningful transitions report existing Organization **DONE / NOW / BLOCKED / NEXT / NEED YOU**. The owner controls cross-repository selection from [Organization TODO.md](https://github.com/opensiro/vsm-oss-organization/blob/main/TODO.md). Upstream is a **rebuildable aggregate** from fork metadata at verified SHA and current first-party external PR reads, not another event store, task scheduler or second VSM. When no data or live readback is available, report **UNKNOWN**, not success/zero.

## External-publication consent

The [historical effective restriction](https://github.com/opensiro/upstream-old/blob/main/docs/EXTERNAL_PUBLIC_COMMUNICATION_GATE.md) still applies: **before every public third-party issue/comment/reply/PR/review/design question or public fork-local proposal**, present exact destination, specific action, final public text and verified code diff as applicable and obtain explicit current-conversation consent.
